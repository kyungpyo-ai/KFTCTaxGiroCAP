# 3차 범위(운영 기능) 개발 로드맵 — Phase 22~25, 27~28

> 요구사항 정본은 같은 폴더의 `PRD.md`다. Task 단위 작업 지시/완료 조건은 각 Phase 착수 직전에
> `development_plan.md`에 작성한다. **Phase 번호는 1차(0~6, `docs/home_reader_setup/ROADMAP.md`),
> 2차(7~21·26, `docs/payment_relay/ROADMAP.md`)에서 이어진다** — 같은 앱을 계속 확장하는 것이므로
> 번호를 새로 시작하지 않는다.
>
> **번호가 25 → 27로 이어지는 것이 건너뛴 것으로 보이지만 아니다.** 26은 2차 범위(거래 상태 조회
> 전문, `docs/payment_relay/ROADMAP.md`)에 속한다. 이 문서가 22~25와 27~28을 함께 다루는 이유는
> Phase 27이 **Phase 22(로그 출력)가 만든 구조를 정정하는 작업**이라 같은 문서에 두는 것이 맞기
> 때문이다(§1.8·§1.9가 §1.3-d·§1.4를 대체한다).

## 작업 방식

1. **반드시 순서를 따른다.** 각 Phase의 "완료 기준"을 통과한 뒤에만 다음으로 넘어간다.
2. **PRD와 구현이 어긋나면 코드보다 먼저 PRD를 갱신한다.**
3. **미확정 사항은 해당 Phase 착수 전에 확인하고 PRD에 반영한다.** 추측으로 진행하지 않는다.
4. 계층 규칙(`Views` → `ViewModels` → `Services` → `Protocol` → `Interop`)을 지킨다. **예외**:
   `Security/SecureClear`(Phase 25 P25-1)는 아무것도 참조하지 않는 leaf 유틸리티라 어느 계층에서든
   호출할 수 있다(`Interop`과 같은 위치의 공용 도구로 취급, `PRD.md` §4.3.1).

## Phase 순서를 이렇게 잡은 이유

- **로그(22)가 먼저**인 이유: 나머지 두 Phase의 디버깅 기반이고, 앱 전체를 가로지르는 관심사라
  나중에 넣으면 이미 작성된 코드를 다시 훑어야 한다. 현재 로그 호출 지점이 151곳이다.
- **키다운로드(24)가 세 번째**인 이유: `FNAISCRDVAN`의 Mode 인자를 Phase 23의 가맹점 설정값에서
  받아야 한다. (서버 구간 SPEC 미확정은 2026-08-31에 해소됐다.)
- **메모리 클리어(25)가 마지막**인 이유: 이미 동작이 검증된 결제 Flow의 타입을 바꾸는 작업이라,
  기능이 다 들어온 뒤에 해야 회귀 여부를 판단할 기준(정상 동작하는 상태)이 존재한다. 22~24에서
  새로 추가된 코드까지 한 번에 같은 방식으로 정리할 수 있다는 이점도 있다.
  (이 Phase는 2026-09-03 인증 시험 기준을 확보하면서 착수가 확정됐다 — PRD §4.1.)
- **장애정보 보고 준비(27)가 나중인** 이유: 계획된 순서가 아니라 **정정 작업**이라서다. Phase 22가
  장래를 예상해 미리 만든 장치 두 개(링버퍼·패턴 마스킹)의 전제가 틀렸다는 것이, 22~26을 실제로
  운용하며 로그를 쌓아 본 뒤에야 실측으로 드러났다(2026-09-09). 먼저 만들 수 있었던 일이 아니다.

## Phase 25 — 카드정보 메모리 클리어 (PRD §4) — 완료(2026-09-03)

**목표**: 인증 시험 기준(민감정보 메모리 삭제)에 맞춰, 카드정보를 **덮어쓸 수 있는 타입**으로 바꾸고
사용 완료 후 **3회 덮어쓰기**한다. 요구사항 정본은 `PRD.md` §4 — 그 절이 근거(인증 기관 안내 원문),
현황 전수 조사표, 방침, 알려진 한계를 모두 담고 있다.

> **왜 이 Phase가 생겼나** — 2026-09-02 Phase 24 계획 중, `ReaderSerial.dll`은 콜백 반환 즉시 자기
> 내부 버퍼를 `SecureZeroMemory`로 지우지만(`docs/reader_dll/API명세서.md` §7) **그 경계를 넘어온
> managed 데이터를 지우는 코드가 이 저장소에 하나도 없다**는 것이 드러나 항목만 기록해 뒀다.
> 2026-09-03 사용자가 인증 시험 기관 안내(현행 DoD 3회 덮어쓰기 / 개정 예정 1회+해제·GC,
> `string` 대신 `byte[]`·`char[]` 권고)를 확보하면서 착수 근거와 구체적 기준이 확정됐다.

> **Phase 24와의 관계** — 키다운로드 경로는 이미 `Array.Clear`(1회)로 지우고 있다. 이 Phase에서
> **같은 `SecureClear`(3회)로 교체해 방식을 통일한다**(PRD §4.3.5). 즉 Phase 25는 "기존 결제 Flow의
> 소급 적용"에 더해 "덮어쓰기 방식 일원화"까지 다룬다(2026-09-03 사용자 확정 — 착수 전 스텁에는
> 키다운로드가 대상 밖으로 적혀 있었으나 이때 바뀌었다).

**이 Phase의 위험도** — 이미 실거래 검증을 마친 결제 Flow 전체(카드리딩 콜백 → `CardReadData` →
`PaymentOrchestrator` → `PinFieldEncoder` → POS 응답)의 **타입을 바꾼다.** Phase 23 CP2급 이상으로
회귀 위험이 높고, Phase 24에서 "개선권장을 고치는 리팩터링이 새 치명적 회귀를 만든" 전례가 있다.
그래서 검증은 **수정한 부분이 아니라 결제 Flow 전체 로직**을 대상으로 한다.

### 순서

- [ ] **P25-1 `SecureClear` 헬퍼** — 덮어쓰기의 유일한 지점(PRD §4.3.1). 3회, 마지막 패스 `0x00`,
      횟수는 상수 하나. `byte[]`/`char[]` 오버로드, `null`·빈 배열 무해 통과. JIT 최적화에 덮어쓰기가
      제거되지 않는 구현 방식을 확정하고 **Release 빌드 실측으로 확인**한다(PRD §4.4 #4)
- [ ] **P25-2 키다운로드 경로 소급 적용** — 기존 `Array.Clear` 호출 8곳을 `SecureClear`로 교체
      (PRD §4.3.5). 호출부 구조 무변경. Phase 24의 `--keydown-test` 하네스가 그대로 통과하는지 확인
- [ ] **P25-3 타입 변경 ①: `CardReadData`** — 19개 필드 전부를 `char[]`/`byte[]` 기반으로 전환
      (PRD §4.3.2). `CardReadResponseParser`, `CardReadCommandOutcome`, `CardReadRoundResult`까지
      연쇄 변경. **이 Task가 이 Phase에서 가장 넓게 번진다**
- [ ] **P25-4 타입 변경 ②: PIN 경로** — `PaymentNoticeViewModel._pinDigits` → `PinEnteredEventArgs`
      → `CollectPinAsync` → `PaymentOrchestrator`의 `pin` → `PinFieldEncoder`까지 `string` 제거
      (PRD §4.2 #5·#6). `PinFieldEncoder`는 SEED 암호화가 확정되면 본문이 바뀔 자리이므로
      (`docs/payment_relay/PRD.md` §10) 격리 구조를 깨지 않는다
- [ ] **P25-5 임시 버퍼 즉시 클리어** — PRD §4.2의 #1, #2, #8, #9, #12, #13을 만든 메서드 안에서

      표로 기록한다. **구조는 바꾸지 않고, 마스킹 누락이 발견된 곳만 고친다**(2026-09-03 사용자 확정).
      `LogRingBuffer`(최근 500건 메모리 상주), `TelegramLogRedactor`의 `#46`/`#51` 처리, 키다운로드
      VAN 구간 원문 로깅(§3.6)을 반드시 포함
- [ ] **P25-9 진단 하네스(심사 증적)** — `--payment-flow-test`/`--keydown-test`와 같은 방식의 CLI

      (PRD §4.6). 심사에서 실증을 요구받으면 이것을 그대로 돌린다

Phase 22~24와 같은 **Opus 다회 리뷰 루프**(dev 구현 → Opus 전체 검증 → 수정 → 재검증 반복,

## Phase 27 — 장애정보 보고 준비 (PRD §1.8·§1.9) — 착수 전

**목표**: 장애 보고에 실을 로그 조각을 **인메모리 링버퍼가 아니라 로그 파일에서 슬라이스**해

> **왜 이 Phase가 생겼나** — Phase 22가 "장래 장애정보 서버 전송을 붙일 수 있는 구조"로 정비한 다섯

> ① §1.3-d가 링버퍼를 둔 근거("파일 되읽기는 잠금·인코딩 문제가 있다")는 §1.3-e가 이미 `FileShare.Read`를
> 계약으로 못박아 둔 것과 모순이고, ② §1.4의 패턴 마스킹은 카드 데이터를 하나도 못 잡으면서 전문
> 헤더를 오탐해 **전문구분과 응답 코드를 가리고 있었다**(§1.9.2 실측).
>
> 전송 기능 자체는 이 Phase의 범위가 아니다 — Phase 28로 분리했다. **다만 판정은 이 Phase에서
> 한다**(2026-09-10 사용자 결정) — 서버로 보내지 않더라도 "이 건은 알림 대상"이라고 로그에
> **`ALERT` 레벨**로 남기는 데까지다(`fault_alert_catalog.md` §1). 판정이 미리 돌아야 임계값 조정용
> 데이터가 쌓인다.

**이 Phase의 위험도** — 원래는 Phase 22~26 중 가장 낮았다(손대는 범위가 `Services/Diagnostics/`
안으로 한정되고, 제거 대상 둘 다 호출부가 없거나 동작이 무해한 방향이라 회귀가 기능 손실로
나타나지 않는다). **2026-09-10에 P27-8(로그 코드 체계 정비)이 추가되며 성격이 달라졌다** — 그 안의 (f)가 POS에 나가는
응답을 새로 만든다.

**조용히 잘못되는 세 가지**를 각별히 본다.

1. **파일 공유 모드 충돌**(§1.8.4 #4) — 리더가 파일을 잘못 열면 로그 기록이 실패하는데, 로깅 실패는
   설계상 조용히 무시되므로 **증상 없이 로그가 비는** 형태로 나타난다.
2. **마스킹 계층 축소**(§1.9.6) — 카드 데이터 유출은 나타났을 때 이미 늦다. 전수 점검을 완료 조건에 넣는다.
3. **`E42`/`E43` 신설 ★**(P27-8-f) — **이 Phase에서 POS 계약이 바뀌는 유일한 지점**이다. 지금까지

### 왜 "제거"부터가 아니라 "대체재 확보"부터인가

링버퍼를 먼저 지우면 그동안 로그 조각을 뽑을 방법이 없는 구간이 생긴다. 실제로는 조회 호출부가
0곳이라 기능적 공백은 없지만, 순서를 뒤집을 이유도 없다 — **대체재가 하네스로 검증된 뒤에(CP1)
제거**한다.

마스킹 제거(§1.9)를 같은 Phase에 묶은 이유는, 둘 다 "Phase 22가 장래를 예상해 미리 만든 장치가
실제로는 불필요하거나 해로웠다"는 같은 성격의 정정이고 둘 다 `FileLogger` 파이프라인 한 곳을
건드리기 때문이다. 나누면 같은 파일을 두 번 열고 전수 점검(P27-7)도 두 번 돌아야 한다.

## Phase 28 — 장애정보 서버 전송 (PRD §1.10) — 보류

**보류 사유**: 수집 서버 스펙이 없다. 아래가 정해져야 착수할 수 있다(`PRD.md` §5 미확정 #11).

- **payload 형태** — JSON 본문에 로그를 문자열로 실을지, multipart 파일 파트로 보낼지
- **엔드포인트·인증 방식·재시도 정책**

**Phase 27이 준비해 두는 것**: "지정한 범위의 로그 줄을 텍스트로 뽑아주는 함수". 위 셋이 어떻게
정해지든 그 위에 얹기만 하면 된다 — 이것이 §1.8.3-(c)에서 반환 형태를 **텍스트 원문**으로 못박은
이유다.

**Phase 28에서 다룰 것**(§1.11의 "하지 않는 것"이 그대로 넘어온다): 장애 보고 봉투 조립(§1.6.1의
6개 항목), 실제 API 호출, 전송 재시도 큐, 오프라인 보관, 압축, 필요하다면 원격 `ILogSink` 구현.

**여기에 코드 체계 마무리가 더해진다**(`PRD.md` §1.12.7, 2026-09-10 추가). Phase 27이 규칙만 확정하고 남겨
둔 것들이다.

- **조건 배포** — **서버가 조건을 내려주는 것이 최종 목표다**(2026-09-10 확정). 판정은 단말,
  규칙은 서버. 장애를 올릴 때 그 **응답에 조건을 실어 보내는** 방식이면 별도 채널이 필요 없다.
  그때까지는 코드 기본값을 쓰고, 서버 값이 오면 그쪽이 이긴다(미도달 시 폴백으로 계속 유효)
- **전송 실패 시 재시도 큐** — 트리거가 "판정 즉시"라 망 단절 구간이 문제가 된다

> **결제 경로를 막지 않는다 ★**(`PRD.md` §1.12.6, 2026-09-10 확정) — 판정·슬라이스·전송을 전부
> **POS 응답을 보낸 뒤 별도 스레드에서** 처리한다. 수집 서버가 느리면 POS 응답이 늦어지는 구조를
> 만들지 않는다. **완료 조건에 "수집 서버를 죽여 놓고 결제가 정상 속도로 끝난다"를 넣는다.**

**2026-09-10에 확정된 것들**(더는 Phase 28의 미결이 아니다) — 판정 주체 **단말**, 전송 트리거
**판정 즉시**, `S01`~`S11` 부여, `E42`/`E43` 신설, 임계값 잠정 확정, 카운터 **리셋 허용**,
슬라이스 범위 **직전 거래 3건부터 로그 끝까지**(상한 200줄). 전부 `fault_alert_catalog.md`가 정본이다.

**남은 미결은 payload 형태 하나**(`PRD.md` §5 #11) — JSON 문자열이냐 multipart 파일 파트냐는
**수집 서버와 합의해야** 정해진다. 슬라이스 결과가 텍스트 원문(§1.8.3-c)이라 어느 쪽이든 그대로
얹힌다.

> **1단계 동안은 조건을 바꾸려면 재배포가 필요하다.** 판정 주체가 단말이고 조건값이 코드에
> 들어가서 생기는 제약이며, 서버 배포가 붙으면 해소된다(`fault_alert_catalog.md` §1). 그때까지는
> 잠정 임계값을 **보수적으로** 잡아 버틴다. **Phase 27은 값을 읽는 지점을 한 곳에 모으는 것까지만
> 한다** — 그것이 서버 값으로 갈아 끼울 이음매다.

> **알림은 레벨이 아니라 code 값으로 건다**(§1.12.4). 거래 결과 코드를 실은 중앙 확정 로그
> (`PaymentOrchestrator.cs:198`)가 **`INFO`** 라서, `ERROR`만 필터링하는 규칙은 `D01`/`R2x`/`E99`를
> 놓친다. 이 사실이 P27-8(레벨 정정)과 `fault_alert_catalog.md` §2(코드별 판정 표)의 근거다.

> **Phase 27과 28을 나눈 이유**: 27은 **지금 확정할 수 있는 것만** 다룬다. 로그가 파일에 있고 거기서
> 구간을 뽑을 수 있으면 되고, 이건 수집 서버가 어떻게 생겼든 바뀌지 않는다. 반면 28은 전부 합의가
> 필요한 값이라 지금 만들면 다시 만들게 된다 — **Phase 22가 링버퍼로 겪은 실패가 정확히 그것이다.**
