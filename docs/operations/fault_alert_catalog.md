# 장애 알림 대상 카탈로그

> **이 문서가 알림 대상과 조건값의 정본이다.** 단말(원캡)이 장애로 판정해 서버에 올릴 대상을 코드
> 단위로 관리한다. 조건을 바꾸거나 새 코드를 추가할 때는 **이 문서를 먼저 고치고** 코드에 반영한다.
>
> **왜 별도 문서인가** — 이 목록은 요구사항이 아니라 **운영하면서 계속 바뀌는 대장**이다. 기능이
> 추가되면 판정 대상이 늘고, 운영 데이터가 쌓이면 임계값이 조정되며, 오탐이 많으면 한동안 끄기도
> 한다. Phase 문서(`PRD.md` / `ROADMAP.md` / `development_plan.md`)에 섞어 두면 그 Phase가 끝난 뒤
> 아무도 갱신하지 않는다.
>
> 판정 **원칙**과 코드 **체계**는 `PRD.md` §1.12에 있다(그쪽은 잘 안 바뀐다). 이 문서는 그 원칙을
> 적용한 **결과 목록과 조건값**이다.

- **최초 작성**: 2026-09-10 (Phase 27 준비 중)
- **상태**: 값은 전부 채워져 있다. **`잠정` 표시된 값은 운영 데이터로 조정할 대상**이며, 비어 있는
  값이 아니다 — §6 참고.
- **아직 이 문서를 읽는 코드는 없다.** 판정·전송 구현은 Phase 28이다.
- **관련 문서**: `PRD.md` §1.12(코드 체계·판정 원칙) · `ROADMAP.md` Phase 28

## 1. 판정 규칙 요약

상세는 `PRD.md` §1.12.4. 실무에 필요한 것만 옮긴다.

**알림 여부는 로그 레벨이 아니라 code 값으로 판정한다.** 거래 결과 코드를 실은 중앙 확정 로그
(`PaymentOrchestrator.cs:198`)는 `INFO` 레벨이다 — `ERROR`만 거르는 규칙은 `D01`/`R2x`/`E99`를
놓친다.

**판정 주체는 단말이다.** 원캡이 이 표를 적용해 **장애로 판정한 건만** 올린다. 서버가 전부 받아
거르는 방식이 아니다.

**조건 값은 지금은 코드의 기본값을 쓰고, 장래에는 서버가 내려준 값을 쓴다**(2026-09-10 사용자
확정). §3의 값이 그대로 코드에 들어가는 것이 1단계다.

**최종 목표: 서버가 조건을 내려준다.** 판정은 단말이 하되 **규칙은 서버가 관리**하는 형태다.
단말이 장애를 올릴 때 그 **응답에 조건을 실어 보내면** 별도 채널도 필요 없다 — 단말은 받은 값을
캐시해 다음 판정부터 쓴다.

```
1순위  서버가 내려준 값 (캐시)        ← 장래
2순위  코드의 기본값 (§3)             ← 지금. 서버 응답 전·서버 미도달 시에도 계속 유효
```

이러면 판정 주체가 단말이라 생기는 유일한 약점(**조건을 바꾸려면 단말에 닿아야 한다**)이 해소된다.
임계값 조정이 서버에서 끝난다.

**지금 서버 배포를 안 하는 이유** — 수집 서버 자체가 아직 없고 payload 형태도 미정이다
(`PRD.md` §5 #11). 서버가 생긴 뒤 그 위에 얹는다.

**그래서 지금 지켜야 할 것 하나** — **값을 읽는 지점을 한 곳에 모은다.** 호출부에 숫자를 흩지
않는다. 이것이 나중에 서버 값으로 갈아 끼울 **이음매**다. 이 제약을 어기면 서버 배포를 붙일 때
전 호출부를 다시 훑어야 한다.

**중간 단계로 검토했다가 접은 것들**

| 방법 | 접은 이유 |
|---|---|
| 레지스트리에서 읽기 | **현장 사용자가 regedit을 열 일이 없다.** 단말이 여러 대면 `.reg` 배포도 사람이 붙어야 해 비현실적 |
| 앱 안에 설정 화면 | 임계값을 판단할 사람이 현장에 없다. **서버 배포가 되면 필요 자체가 없어진다** — 그때 가서 판단한다(만든다면 `ShopSetupWindow`에 탭, `PRD.md` §2.1의 "탭 없음" 결정을 함께 뒤집어야 함) |

**대가(1단계 동안): 값을 바꾸려면 재배포가 필요하다.** 그래서 §3의 잠정값을 **보수적으로(오탐이
적게) 잡았다** — 자주 못 바꾸므로 시끄러운 쪽보다 조용한 쪽으로 기울인다.

### 지금은 판정까지만 하고 로그에 표시한다 (Phase 27)

**서버 전송이 없어도 판정은 지금 한다**(2026-09-10 사용자 확정). 판정 결과를 **로그에 한 줄로
남기는 것**까지가 Phase 27이고, 그 줄을 서버로 보내는 것이 Phase 28이다.

**왜 미루지 않는가** — §3의 임계값을 "운영 로그 4주 축적 후 조정"하기로 했는데, **판정이 미리
돌면서 로그를 남기면 그 데이터가 바로 쌓인다.** 전송까지 만든 뒤에 판정을 붙이면 그때부터 4주를
다시 기다려야 한다. 또 Phase 28이 순수하게 "보내기"만 남아 서버 스펙이 나오는 즉시 붙는다.

**표시 형식 — `ALERT` 레벨을 신설한다**(2026-09-10 사용자 확정). 알림 대상으로 판정된 건에만
한 줄 남긴다.

```
[2026-09-10 14:23:01.482] [ERROR] [Van    ] [-  ] [240910001234] [VanService] DLL 로드 실패: ...
[2026-09-10 14:23:01.485] [ALERT] [Van    ] [D01] [240910001234] 장애 알림 대상 — VAN DLL 로드 실패
[2026-09-10 15:02:11.007] [ALERT] [Reader ] [R05] [240910001235] 장애 알림 대상 — 임계값 초과(1시간 12건 > 10건)
```

- **`LogLevel`에 `ALERT`를 추가한다.** 레벨 슬롯이 폭 5인데 `ALERT`도 5자라 **패딩 없이 딱 맞고
  로그 포맷이 바뀌지 않는다**(`PRD.md` §1.11 — 5슬롯·폭 그대로).
- **`ALERT`는 최상위 심각도다** — `INFO` < `WARN` < `ERROR` < `ALERT`(`PRD.md` §1.5). 별개의
  축이 아니라 `ERROR`보다 한 단계 위다: `ERROR`는 "기능이 손실됐다"까지고, `ALERT`는 **"그래서
  사람이 개입하지 않으면 복구되지 않는다"** 까지다.
- **§1.5의 `ERROR` 기준을 함께 조정했다**(2026-09-10) — 원래 `ERROR` 판단 기준이 "새벽에 깨울
  만한가"였는데 **그게 곧 알림 기준**이라 `ALERT`로 올렸다. 알림 판정과 로그 레벨이 같은 질문을
  두 번 묻지 않게 된다.
- **레벨 슬롯만으로 걸러진다** — 메시지 파싱이 필요 없고, 실패 건수와 알림 건수를 따로 셀 수 있다.
- **code 슬롯에 유발 코드를 채운다** — 어떤 코드가 알림을 유발했는지가 판정의 핵심 정보다.
- **카테고리는 원인 서브시스템을 그대로 쓴다**(`Van`/`Reader`/`Pos`…). `App`으로 뭉치지 않는다 —
  어느 계통 고장인지가 알림의 1차 분류다.
- **알림 대상이 아닌 건은 남기지 않는다.** `E01`(사용자 취소)마다 "알림 아님" 줄을 찍으면 로그가
  두 배가 된다. 발생 횟수는 어차피 기존 거래 확정 줄로 셀 수 있다.
- **급증형(`T`)은 임계값을 넘은 시점에만** 한 줄 남기고, 넘긴 값을 메시지에 적는다.

> **급증형이 이 경계를 잘 보여준다** — `R05` 개별 건은 재요청 라운드가 남아 `WARN`, 1시간 12건이
> 되어 리더기 고장이 확실해진 시점이 `ALERT`다. 자연스러운 에스컬레이션이며, 장래 "`WARN` 이상만"
> 같은 필터를 만들어도 `ALERT`가 당연히 포함된다.

> **호출부가 직접 `ALERT`를 쓰지 않는다.** 개별 실패 지점은 지금처럼 `WARN`/`ERROR`로 남기고,
> 알림 대상인지는 판정 로직만 정한다. 이 규칙이 없으면 "심각해 보이니 `ALERT`로 찍자"가 번져
> 카탈로그와 로그가 갈린다.

**거래 경계(빈 줄)는 `ALERT` 뒤로 미룬다**(2026-09-10 사용자 확정). `FileLogSink`가 "거래 확정"
메시지 뒤에 넣는 구분선(`:55-59`)을 그대로 두면, 판정이 백그라운드라 `ALERT` 줄이 **경계 바깥으로
떨어져 다음 거래 블록 머리에 붙는다.**

```
[INFO ] … [PaymentOrchestrator] 거래 확정
[ALERT] … 장애 알림 대상 — VAN DLL 로드 실패
                                                ← 빈 줄은 여기
[INFO ] … 다음 거래 시작
```

**한 거래의 모든 줄이 한 블록에 모여야 한다** — 사람이 읽을 때 오독하지 않고, "직전 거래 N건"
슬라이스(§3)가 경계를 잡을 때도 어긋나지 않는다.

- **판정이 끝났다는 신호가 필요하다.** 판정이 비동기라 "거래 확정" 시점에는 `ALERT`가 뒤따를지
  알 수 없다. 구분선 삽입 조건을 **"거래 확정"에서 "그 거래의 판정 완료"로 옮긴다.**
- **알림 대상이 아닌 거래**(대다수)도 판정은 끝나므로 경계는 정상적으로 찍힌다.
- 구현 방식(판정부가 경계를 직접 남길지, `FileLogSink` 조건을 바꿀지)은 P27-9에서 정하고 기록한다.

**Phase 28이 할 일** — 이 판정 결과를 받아 로그 조각(§3)과 함께 서버로 보낸다. 판정 자체는 다시
만들지 않는다.

### 결제 경로를 막지 않는다 ★

**알림 판정·로그 슬라이스·서버 전송은 결제 응답 경로를 절대 막지 않는다**(2026-09-10 사용자 확정).
POS 응답을 **보낸 뒤** 별도 스레드에서 fire-and-forget으로 처리하고, 실패해도 결제 결과에 영향을
주지 않는다. **Phase 27의 판정·로그 표시도 이 제약을 그대로 따른다** — 전송이 없어도 판정과
카운터가 결제 스레드 위에서 돌면 안 된다.

**왜** — 트리거가 "판정 즉시"(§3)인데 그 "즉시"를 결제 스레드 위에서 하면, 수집 서버가 느리거나
응답이 없을 때 **POS가 받는 응답이 그만큼 늦어진다.** 장애 알림이 결제를 망치는 셈이 된다.
부하 자체는 작다(슬라이스 약 40KB 읽기 + HTTP 1회) — **문제는 크기가 아니라 결제 스레드가
기다리느냐**다.

**지킬 것**

- 판정 결과가 나온 뒤 전송을 **예약**만 하고 결제 흐름은 즉시 진행한다. `PaymentOrchestrator`가
  리더기 초기화를 백그라운드로 예약하는 방식(`:1017`)과 같다.
- 전송 실패·타임아웃·예외가 **결제 응답을 바꾸지 않는다.** 로그만 남긴다.
- 슬라이스(파일 읽기)도 전송과 함께 백그라운드로 넘긴다 — 결제 스레드에서 파일을 읽지 않는다.
- 알림이 폭주해도 결제가 느려지지 않아야 한다. 동시 전송 수를 제한하거나 큐를 쓴다.

> **이 제약이 지켜지는지 Phase 28 완료 조건에 넣는다.** 실장비에서 수집 서버를 일부러 죽여 놓고
> 결제가 정상 속도로 끝나는지 확인하는 것이 가장 확실한 검증이다.

**판정 축 두 개**

| 축 | 내용 |
|---|---|
| 조치 주체 | 사용자 행동·현장 설정 문제면 알리지 않는다(원격으로 할 수 있는 일이 없다). 원격 개입이 필요한 고장만 알린다 |
| 발생 양상 | 단발은 정상인데 몰리면 장애인 코드가 있다. 이 축에 걸리면 **임계값이 필요하다** |

### 2.2 `S` 계열 — 전문이 나가지 않는 내부 사건

### 2.3 `E42` / `E43` — 침묵하던 경로를 응답으로 바꾼다

**2026-09-10 사용자 확정. 아직 구현되지 않았다 — Phase 27(P27-9)에서 만든다.**

지금은 아래 두 경우에 원캡이 **아무 응답 없이** 프레임을 버리거나 연결을 끊는다. POS는 왜 응답이
없는지 알 방법이 없어 타임아웃만 난다. `S` 코드로 우리만 아는 것보다 **POS에게 이유를 알려주는
편이 낫다.**

| 코드 | 상황 | 지금 | 바꿀 것 |
|---|---|---|---|
| `E42` | 본문이 16바이트 미만이라 `#4`(거래 구분 코드)를 못 읽음 | `PosRequestTelegram.cs:55`에서 예외 → `PosSocketServer.cs:286`이 프레임만 폐기, 침묵 | `E41`이 쓰는 `PosUnknownTransactionErrorResponse.Build()`로 **최소 공통부 응답**을 만들어 회신 |

**응답이 가능한 근거** — `E41`(스키마 미식별)이 이미 "전문 종류를 몰라도 최소 공통부만으로 응답한다"
는 방식을 쓰고 있다(`PosRequestTelegram.cs:65`). 같은 메커니즘을 그대로 쓴다.

**`E43`도 대응 관계가 명확한 근거**(2026-09-10 사용자 지적으로 정정) — 처음에는 "프레이밍이 깨지면
어느 요청의 응답인지 POS가 모른다"고 봤으나, **POS 원칙이 "1왕복 후 종료"**다
(`docs/payment_relay/PRD.md:812`). 연결 하나에 전문 하나이므로 그 연결에 쓴 응답은 대응이 명확하다.
서버가 다중 프레임을 처리하는 것은 POS가 원칙을 어겨도 죽지 않게 하려는 방어일 뿐이다.

**POS 통보 필요** — `E42`/`E43`은 SPEC에 없는 자체 코드다. 다만 **`E40`/`E41`이 이미 같은 처지**라
새로 생기는 문제는 아니다. POS 담당자에게 알려야 하며, 이 항목을 `PRD.md` §5 미확정에 남긴다.

**전환 후 알림 판정** — `E42`/`E43`은 POS가 응답을 받으므로 `S` 계열이 아니다. **판정은 §2.1 표에
등록해 뒀다**(기존 `E40`/`E41`과 나란히, 넷 다 `T`). 둘 다 **원인이 POS 쪽**(잘못된 요청을 보냄)이라
우리 장애가 아니지만, **정상 POS라면 나올 수 없는 값**이므로 임계값 초과 시에만 알린다 — 반복되면
POS 펌웨어 문제이거나 다른 무언가가 8002에 붙은 것이다. 임계값은 §3.

### 값의 근거

**`E05` 1시간 3건** — 무결성 체크는 정상 상태에서 거의 실패하지 않는 사건이다. 3건이면 이미
일시적 잡음으로 보기 어렵다. 오탐이 나오면 올린다.

**`R0x` 1시간 10건** — 카드 불량·사용자 실수가 섞여 정상 상태에서도 꾸준히 발생한다. 정상 빈도를
모르므로 **보수적으로(높게) 잡아 오탐을 피하고**, 운영 데이터를 보며 내린다. 놓치는 쪽이 시끄러운
쪽보다 낫다 — `R2x`(DLL 실패)는 어차피 단발로도 잡히므로 진짜 리더기 고장은 다른 경로로 뜬다.

**`S09` 1시간 5건** — 키오스크 1대에 POS 1대 환경이라 정상 연결은 1~2개다. 상한 16이 차서 거부가
난다는 건 **연결 누수이거나 POS 이상 동작**이다. 단발은 일시적 폭주로 보고 넘기되, 시간당 5건이면
지속적 문제로 판단한다.

**카운터 리셋 허용** — 영속화하면 쓰기 빈도가 늘고 정리 로직이 필요하다. **재시작 자체가 별도
장애 신호로 포착**되므로(앱 기동 로그, `S` 계열) 리셋을 허용해도 장애를 통째로 놓치지 않는다.

**판정 즉시 전송** — 실시간성이 목적이고 구현이 가장 단순하다. 망 단절 시 재시도 큐가 필요한데,
**망 단절 자체가 장애일 수 있다**는 점을 Phase 28 설계에서 다룬다.

**직전 거래 3건부터 로그 끝까지**(2026-09-10 사용자 확정 — 시간창 방식에서 변경) — 시간 기준은
**거래량에 휘둘린다.** 한산하면 3분에 거래 1건, 바쁘면 20건이 잡혀 문맥의 양이 들쭉날쭉해진다.
거래 개수 기준은 부하와 무관하게 일정한 문맥을 준다.

**뒤쪽을 잡지 않는 이유** — 장애가 난 시점 이후로는 거래가 생기지 않는다. 뒤 시간창은 대부분
빈 구간을 긁어오는 낭비다. 대신 **로그 끝까지**(= 전송 시점까지) 가져가면 장애 직후의 정리·초기화
로그가 자연히 포함된다.

- 세는 대상은 **서로 다른 거래ID**다. 거래ID가 `-`인 줄(앱 기동, DLL 로드, 리더기 단절 등)은
  **개수에 세지 않되 결과에는 포함**한다 — 그 줄들이 원인인 경우가 많다.
- 장애 건 자신의 거래ID는 개수에 넣지 않는다. "직전 3건 + 장애 건"이 실린다.
- 크기는 거래 4건 약 40줄에 사이의 비거래 줄을 더해 **대략 10~30KB**. 시간창(80KB)보다 작고
  예측 가능하다.
- **앵커는 문자열 매칭이 아니라 장애 발생 시각이다**(2026-09-10 재확정). POS는 지속 연결·다중
  클라이언트를 허용하고 판정은 결제 경로 뒤 백그라운드에서 돌므로(§1.12.6), 판정이 실행되는
  시점에는 **로그 끝(EOF)이 항상 장애 거래 자신이 아닐 수 있다** — 그 사이 다른 접속의 거래가
  몇 줄 더 찍혔을 수 있어서다. 그래서 `LogFileReader`는 "장애 발생 시각보다 이후인 줄은 건너뛰고,
  그 이하 시각부터 거래ID가 다른 직전 N건을 센다"는 방식으로 동작한다 — 문자열로 자기 ID를
  찾아 헤매지 않는다. 최종 반환은 그렇게 찾은 시작점부터 **실제 EOF까지**이므로, 판정 사이에
  끼어든 무관한 거래가 있어도 그대로 포함된다(§1.8.3-a, `development_plan.md` P27-3).

### 3.1 상한 가드가 필요한 이유

**앞에 거래가 3건 없을 수 있다.** `S01`(소켓 리스닝 실패)처럼 앱 기동 직후 발생하는 장애는 그날
거래가 0건이다. 가드가 없으면 3건을 찾아 파일 처음까지, 다시 어제 파일까지 무한정 거슬러 올라간다.

**최대 200줄까지만 올라간다**(약 40KB, 2026-09-10 사용자 확정). 그 안에서 거래 3건을 못 찾으면
찾은 만큼만 싣는다.

- **정상 운영에서는 이 가드에 걸리지 않는다.** 거래 3건이 약 40줄이고 사이의 비거래 줄을 더해도
  200줄 안에 넉넉히 들어온다. 가드가 실제로 작동하는 건 **거래가 드물거나 없는 상황**뿐이다.
- 기동 직후 장애(`S01`·`S02`)는 앞 거래가 0건이라 항상 이 가드에 걸리는데, **그때 실리는 200줄이
  곧 기동 로그**다 — 기동 실패의 원인은 거기에 있으므로 필요한 것이 실린다.
- 자정 경계 처리(`PRD.md` §1.8.4 #2)는 그대로 유효하되, **이 가드가 먼저 걸리면 어제 파일은 열지
  않는다.** 200줄이면 대부분 당일 파일 안에서 끝난다.
- **모자라면 올린다.** 실제 보고를 몇 건 받아 보고 문맥이 부족하면 조정한다. 1단계에서는
  재배포가 필요하고, 서버 배포가 붙으면 서버에서 바꾼다(§1).

## 4. 새 코드를 추가할 때 (기능 추가 시)

기능이 늘면 판정 대상도 는다. 아래 순서를 따른다.

1. **기존 코드로 표현되는지 먼저 본다.** 거래 경로에서 발생해 POS 응답 전문 `#7`에 실려 나가는
   실패라면 `PosResultCodeMapper`에 코드를 추가하고 **§2.1에 등록한다.** 로그 전용 코드를 따로
   만들지 않는다(`PRD.md` §1.12.2 #1).
2. **전문이 나가지 않는 사건이면 `S` 코드를 딴다.** 3자리 고정, **다음 번호는 `S12`**.
   - **먼저 "응답할 수 있는가"를 따진다.** 응답이 가능하면 `S`가 아니라 `Exx`다 — `E42`/`E43`이
     그렇게 만들어졌다(§2.3).
   - 판정 질문은 **"POS가 결과 코드를 실제로 받는가"** 다. "거래 중이니까 `E99`가 덮겠지"라고
     넘겨짚지 않는다 — 코드가 정해져도 **전달에 실패하면 POS는 못 받는다**(`S06`이 그 경우다).
3. **§1의 두 축으로 판정한다.** 원격 개입이 필요한가? 단발로도 문제인가, 몰려야 문제인가?
4. **표에 행을 추가한다.** 근거 열을 반드시 채운다 — 나중에 판정을 뒤집을 때 근거가 없으면 같은
   논의를 반복하게 된다.
5. `T`로 판정했으면 **§3에 임계값을 넣는다.** 값을 모르겠으면 **비워 두지 말고 잠정값을 넣고
   `잠정`으로 표시**한다(§6) — 비어 있으면 그 코드는 영영 알림이 안 뜬다.
6. **코드의 기본값에 반영한다.** 값을 읽는 지점을 한 곳에 모아 두고 호출부에 숫자를 흩지
   않는다 — **장래 서버 배포로 갈아 끼울 이음매**다(§1).
7. **§7 변경 이력에 남긴다.**

## 5. 이 카탈로그로 잡을 수 없는 것 (알려진 한계)

판정 기준이 **"POS가 결과 코드를 받는가"** 라서, 아래 여섯 유형은 코드 목록으로 덮이지 않는다.
빠뜨린 것이 아니라 **구조적으로 불가능**하므로 다른 수단이 필요하다.

**(1) 앱이 죽거나 멈춘 경우 — 원리적으로 불가능**

판정 주체가 단말인데 그 주체가 사라진 상태다. 로그도 안 남고 알림도 못 보낸다.
**서버 쪽 heartbeat(주기적 생존 신호)와 미수신 감지가 있어야 한다** — Phase 28 수집 서버 설계에서
다룬다(2026-09-10 사용자 확정: 지금은 한계로 명시만 하고 설계는 Phase 28).

**(2) 응답은 정상인데 동작이 틀린 경우**

POS가 `000`이나 `E07`을 정상 수신하므로 code 기준으로는 영원히 안 걸린다. 예:

- `E07`(원거래 없음)이 실제로는 `S03`(무결성/저장소 실패) 때문인 경우
- `TelegramLogRedactor`가 잘못 마스킹해 카드번호가 로그에 남는 경우

**(3) 로깅 자체가 실패한 경우 — 앱 사망과 같은 급이다**

`FileLogger.cs:103`과 `:126`이 로깅 실패를 **조용히 삼킨다.** 디스크 가득참·권한 문제로 로그를 못
쓰면 **그 사실을 포함해 아무것도 남지 않는다.** 로깅 실패를 로깅하면 순환이라 구조적으로 불가능한
것은 맞지만, 결과적으로 **판정의 재료 자체가 사라진다** — 단말이 판정 주체인데 재료가 없으므로
(1)과 같은 사각지대다. **heartbeat로 함께 다뤄야 한다.**

**(4) 전송 실패 구간에 발생한 장애**

트리거가 "판정 즉시"(§3)인데 망이 끊겨 있으면 못 보낸다. 재시도 큐가 Phase 28이라 지금 설계로는
그 구간이 유실된다. **망 단절 자체가 장애일 때 특히 문제**다 — 알려야 할 상황에서 알릴 수단이 없다.

**(5) 카탈로그와 코드가 어긋난 경우**

조건값이 코드에 들어가므로(§1), 이 문서를 고치고 코드에 반영하지 않으면 **문서를 믿는 사람과
실제 동작이 갈린다.** 지금은 확인할 수단이 없다 — 적용 중인 값을 기동 로그에 한 줄 남기는 것이
최소한의 방어다(Phase 28).

**(6) 알림 대상 코드가 붙지 않은 신규 실패 경로**

기능을 추가하면서 §4 절차를 안 따르면 그대로 사각지대가 된다. 그래서 §4를 이 문서 안에 뒀다.

## 6. 잠정값 관리 규칙

**값을 모른다고 비워 두지 않는다.** 비워 두면 그 조건은 동작하지 않고, "나중에 정하자"는 실제로는
"영영 안 정한다"가 된다. 대신 **근거 있는 잠정값을 넣고 상태를 표시한다.**

| 상태 | 의미 |
|---|---|
| `확정` | 근거가 있고 바꿀 이유가 생기기 전까지 유지한다 |
| `잠정` | 값은 동작하지만 **운영 데이터로 조정할 대상**이다. §3의 재검토 조건을 채워 둔다 |
| `잠정(제안)` | 이쪽이 제안한 값이며 **사용자 확정을 아직 못 받았다.** 확정되면 `잠정` 또는 `확정`으로 바꾼다 |

- **재검토 조건을 반드시 적는다**("운영 로그 4주 축적 후" 등). 조건 없는 `잠정`은 방치된다.
- 재검토해서 값을 바꾸지 않기로 했으면 **`확정`으로 승격하고 이력에 남긴다.** 계속 `잠정`으로
  두지 않는다.
- 잠정값이라도 **§3 표에 실제 숫자가 들어가 있어야 한다.** "미정"이라고 쓰지 않는다.
