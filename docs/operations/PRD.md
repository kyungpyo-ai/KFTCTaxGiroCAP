### 0.2 개발 환경 · 계층 규칙

2차 범위와 동일하다. 새로 정할 것이 없으므로 요점만 옮긴다.

- 타겟 `net48`(.NET Framework 4.8), `PlatformTarget=x86`(네이티브 DLL 2종이 Win32 전용).
- **모든 신규 화면은 MVVM**(`docs/payment_relay/ROADMAP.md` "계층 구조"). 창 핸들/OS에 직접 묶인

- 계층 방향: `Views` → `ViewModels` → `Services` → `Protocol` → `Interop`. 역방향 참조 금지.
  `Protocol/`은 DLL 세부사항을 모르고, `Services/`는 WPF 타입에 의존하지 않는다.
- Windows 10 1809+ 전용 API는 OS 버전 체크 후 조건부 적용(Win7 no-op).

## §1 로그 출력 (Phase 22)

### 1.1 현황과 목표

`Services/Diagnostics/FileLogger.cs`가 이미 **일자별 파일 로깅**을 하고 있다.

- 현재 위치: `%LOCALAPPDATA%\KFTCTaxGiroCAP\logs\yyyy-MM-dd.log`
- 형식: `[yyyy-MM-dd HH:mm:ss.fff] [LEVEL] 메시지`
- 프로세스 전역 `lock`으로 직렬화(리더기 CALLBACK이 별도 스레드에서 기록하므로 필요)
- 로깅 실패는 조용히 무시(디스크 가득참·권한 문제로 앱이 죽으면 본말전도)

즉 요구사항 "1일 단위 파일 저장"은 **이미 충족돼 있다.** 이번에 실제로 하는 일은 넷이다.

1. **로그 경로 변경**(§1.1.1) — 현장 접근성 문제 해결
2. **90일 보관 정리**(§1.2)
3. **장애정보 서버 전송을 나중에 붙일 수 있는 구조로 정비**(§1.3)
4. **마스킹 강제**(§1.4)

호출 지점이 현재 **151곳**이므로, 기존 `FileLogger.Info/Warn/Error(string)` 호출은 **그대로 계속
동작해야 한다**(전면 치환 금지). 새 기능은 오버로드와 내부 구조 변경으로 얹는다.

### 1.1.1 로그 경로 변경 및 관리자 권한 상시 실행

**로그 경로를 `C:\KFTC_PosAgent\KFTCTaxLog\`로 바꾼다**(2026-09-01 확정). `%LOCALAPPDATA%`는
탐색기 기본 숨김 폴더라 가맹점·현장 기사가 직접 찾기 어렵다는 문제가 있었다.

이 위치는 사용자 프로필 밖(`C:\` 루트)이라 **일반 권한으로는 쓰기가 안 될 수 있다** — 애초에
`%LOCALAPPDATA%`를 선택했던 이유(§0.3 근거)가 그대로 여기서도 걸린다. 이를 해결하기 위해
**앱을 항상 관리자 권한으로 실행한다**(2026-09-01 확정).

- **`app.manifest`에 `requireAdministrator`를 추가한다.** 이 뒤로 앱을 실행하면 항상 관리자 권한
  상승이 필요해진다(수동 실행 시 UAC 프롬프트가 뜬다).
- **DB 경로(§1.6, SQLite)는 옮기지 않는다** — `%LOCALAPPDATA%\KFTCTaxGiroCAP\`에 그대로 둔다.
  관리자 권한으로 실행되면 쓰기 권한 문제가 어차피 없으므로, 굳이 옮겨서 `IntegrityCheckStore`와
  경로 규칙을 갈라놓을 이유가 없다.
- **설치 시 폴더를 미리 만들어 둘 필요는 없다** — 앱이 관리자 권한으로 실행되므로 최초 기동 시
  `Directory.CreateDirectory`로 스스로 만든다(기존 로직과 동일한 패턴).

**설치 시 반드시 확인해야 하는 5가지**(2026-09-01 확정 — 이 5가지가 모두 갖춰지지 않으면 무인
재부팅 후 앱이 뜨지 않거나 UAC 프롬프트에서 멈춘다. **앱 코드가 아니라 설치 절차의 책임이며, 이
PRD가 요구사항으로 못박아 둔다**):

1. 키오스크 계정에 **자동 로그온**이 설정돼 있을 것
2. 작업 스케줄러 트리거가 **"로그온할 때"**(해당 계정 지정)일 것 — "시스템 시작 시"는 데스크톱
   세션이 없어 창이 뜨지 않는다
3. **"사용자가 로그온한 경우에만 실행"** 옵션일 것 — "로그온 여부와 관계없이 실행"은 세션 없이
   백그라운드로 돌아 창이 안 뜬다
4. **"가장 높은 권한으로 실행"**이 체크돼 있을 것 — 이래야 대화형 UAC 동의 없이 스케줄러가 직접
   토큰을 승격해 실행한다
5. 계정이 **관리자 그룹**에 속해 있을 것, 그리고 기본값 "3일 넘게 실행되면 중지" 옵션을 끌 것
   (키오스크는 계속 켜져 있으므로)

> 이 5가지는 설치 스크립트/설치 매뉴얼에 반영해야 하는 항목이며, 이 저장소의 코드 변경 범위에는
> 없다. `docs/payment_relay/PRD.md`나 별도 설치 문서가 생기면 그쪽으로 옮기는 것을 고려한다.

**5번(관리자 그룹)이 단순 권장이 아니라 이 설계의 필수 전제인 이유**(2026-09-01, P22-0 코드 리뷰
과정에서 확인): "DB 경로를 옮기지 않는다"는 위 결정은 **승격 후에도 로그온 계정이 바뀌지 않는다**는
전제에서만 성립한다. 만약 키오스크 계정이 표준 사용자이고 UAC 동의 시 **다른 관리자 계정**으로
로그온한다면, 그 계정의 `%LOCALAPPDATA%\KFTCTaxGiroCAP\`(SQLite DB, §1.6)와
`HKCU\Software\KFTC_VAN\KFTCTaxGiroCAP`(리더기 설정)가 원래 키오스크 계정의 것과 **다른 프로필로
갈라진다** — 기존 설정·이력이 갑자기 사라진 것처럼 보이는 장애로 이어진다. 그러므로 "키오스크
계정 자체를 관리자 그룹에 넣어, 승격이 별도 계정 전환 없이 같은 프로필 안에서 일어나게 한다"가
반드시 지켜져야 한다.

**Phase 23 "자동 리부팅"(§2.5)과의 관계**: 자동 리부팅 자체는 이번 범위에서 값 저장까지만 하고
실제 동작은 구현하지 않지만(§0.1), 장래 구현 시 위 5가지 전제가 이미 만족돼 있어야 재부팅 후에도
앱이 무인으로 다시 뜬다. 이 전제가 §2.5의 장래 구현을 위한 선행 조건이라는 점을 §2.5에도 기록한다.

**사용자가 앱을 껐다가 바탕화면 아이콘 등으로 직접 재실행하는 경우**(위 5가지 경로를 거치지 않는
실행)에는 UAC 동의창이 뜬다. **별도 우회 장치를 두지 않는다**(2026-09-01 확정) — 계정이 이미
관리자 그룹에 속해 있으므로(5번) 비밀번호 입력 없이 "예" 한 번만 누르면 되고, 이 경로는 드물게만
일어난다. 문제가 되는 것은 사람이 없는 무인 재부팅/재시작뿐이며 그건 위에서 이미 해결됐다.

**단일 인스턴스 보장**(2026-09-01, 실물 검증 중 발견된 gap 보강): 관리자 권한 승격 과정에서 같은
exe가 두 프로세스로 중복 기동되는 현상이 확인됐다 — 하나는 정상적으로 TCP 8002/리더기 COM 포트를
잡고, 다른 하나는 `AddressAlreadyInUse`로 반쪽만 뜬다. `Global\` 네임스페이스 Mutex로 앱 기동
최상단(로그 파이프라인 구성보다 먼저)에서 단일 인스턴스를 체크하고, 이미 다른 인스턴스가 있으면
새 프로세스는 아무 흔적도 남기지 않고 즉시 종료한다.

### 1.2 보관 정리 (90일)

- **90일보다 오래된 로그 파일을 삭제한다.** 기준은 파일명(`yyyy-MM-dd.log`)에서 파싱한 날짜다 —
  `LastWriteTime`은 파일 복사·백업으로 바뀔 수 있어 기준으로 삼지 않는다.
- 파일명이 패턴에 맞지 않는 파일은 **건드리지 않는다**(사용자가 넣어둔 파일을 지우지 않기 위함).
- 실행 시점: **앱 기동 시 1회** + **날짜가 바뀌어 새 로그 파일을 처음 만들 때**. 별도 타이머를 두지
  않는다(24시간 이상 켜져 있는 키오스크에서도 날짜 전환 시 자동으로 걸린다).
- 정리는 **백그라운드에서** 수행하며, 실패(파일 잠김 등)는 조용히 무시하고 다음 기회에 다시 시도한다.
  기동 경로를 블로킹하면 안 된다.
- 보관 기간 90일은 상수로 한 곳에 둔다(장래 설정화면 노출 가능성 대비).

### 1.3 장애정보 서버 전송 대비 구조

> 전송 기능 자체는 이번 범위가 아니다. 다만 **나중에 붙일 때 로그를 전부 다시 손보는 일이 없도록**
> 아래 다섯 가지를 이번에 정비한다.

**(a) 싱크 추상화** — 현재 `static class FileLogger`가 파일 쓰기를 직접 한다. 로그 한 건을 받는
`ILogSink` 인터페이스를 두고 파일 싱크를 그 구현으로 만든다. 장래의 원격 싱크는 같은 인터페이스로
**병렬 추가**한다(파일 기록은 원격 전송 성공 여부와 무관하게 항상 수행된다). `FileLogger`의 공개
정적 메서드는 그대로 두고 내부에서 싱크에 위임하는 형태로 유지한다 — 151곳을 고치지 않기 위함이다.

**(b) 기계 파싱 가능한 라인 포맷** — 서버가 로그를 받아 원인별로 집계하려면 사람이 읽는 문장만으로는
부족하다. 로그 한 줄은 **고정된 5개 대괄호 슬롯 + 자유 메시지**로 구성한다.

```
[시각] [레벨] [카테고리] [코드] [거래ID] 메시지
```

**렌더링 규칙**

- **슬롯은 항상 5개가 모두 존재한다.** 값이 없으면 생략하지 않고 `[-]`로 채운다 — 슬롯이 사라지면
  위치 기반 파싱이 깨진다.
- 슬롯 값에는 `[`/`]`를 넣지 않는다(모두 열거형·고정 코드·전문관리번호라 자연히 지켜진다). 거래ID는
  POS가 보낸 소켓 원시 바이트에서 온 값이라 전문 파싱이 문자셋을 검증하지 않으므로, 개행이 섞여도
  "한 레코드 = 한 줄" 계약이 깨지지 않도록 렌더러가 `[`/`]`/개행을 코드 레벨로 이스케이프한다
  (`LogLineRenderer.SanitizeSlot`).
  **메시지는 마지막 필드이므로 무엇이든 담을 수 있다** — 대괄호를 포함해도 파싱에 영향이 없다.
- 파싱 정규식(장래 서버·분석 도구가 쓸 계약):
  `^\[([^\]]*)\] \[([^\]]*)\] \[([^\]]*)\] \[([^\]]*)\] \[([^\]]*)\] (.*)$`
  레벨/카테고리/코드 슬롯은 모두 Trim 후 비교한다(아래 예외 규칙 때문에 각각 고정폭으로 패딩돼 있다 —
  장래 서버 파싱 계약).
- 슬롯 사이 구분자는 공백 1개. 패딩(정렬용 공백 채움)을 넣지 않는다 — 눈에는 예쁘지만 파싱 시
  trim 처리가 하나 더 필요해진다. **단, 레벨·카테고리·코드·거래ID 네 슬롯은 예외로 고정폭 좌측정렬
  패딩을 쓴다**(2026-09-01 확정, `LogLineRenderer.cs`) — 값 종류가 적거나(레벨·카테고리·코드) SPEC이
  정의한 고정 자릿수가 있어서(거래ID) 파서가 `Trim()` 한 번으로 끝나고, 사람이 읽는 정렬 이득이 크다.
  - 레벨: 폭 5(`INFO `/`WARN `/`ERROR`).
  - 카테고리: 폭 8(`SETTINGS` 등 §1.3-b 카테고리 표 8종 중 최장 기준). 빈 슬롯(`-`)도 이 폭에 맞춰
    패딩한다.
  - 코드: 폭 3(`PosResultCodeMapper`가 만드는 `E0x`/`R0x`/`R2x`/`D0x` 체계가 전부 3자리 — 위 "코드"
    절 참고). 빈 슬롯(`-`)도 이 폭에 맞춰 패딩한다.
  - 거래ID: **최소**폭 12(SPEC `#9` 전문관리번호 `AN(12)` 기준, `PosCommonHeader` 필드 정의 참고) —
    최대폭이 아니라 최소폭이다. `PaymentOrchestrator.LogTxId`의 fallback 값(`{전문구분}-NOID-{해시}`)처럼
    12자를 넘는 값은 자르지 않고 그대로 늘어난다.

**필드 정의**

| 슬롯 | 값 | 비고 |
|---|---|---|
| 시각 | `yyyy-MM-dd HH:mm:ss.fff` | 로컬 시각. 현재 형식 유지 |
| 레벨 | `INFO` / `WARN` / `ERROR` | 현재 3단 유지. **폭 5 고정 패딩**(`INFO `/`WARN `/`ERROR`) |
| 카테고리 | `APP` `POS` `READER` `VAN` `PAYMENT` `KEYDOWN` `UI` `SETTINGS` | 아래 표. **폭 8 고정 패딩**(`SETTINGS` 기준, 2026-09-01) |
| 코드 | 3자리 결과 코드 또는 `-` | **기존 `PosResultCodeMapper` 체계를 그대로 쓴다**. **폭 3 고정 패딩**(2026-09-01) |
| 거래ID | 전문관리번호 또는 `-` | 아래 (c). **최소폭 12 고정 패딩**(SPEC `#9` `AN(12)` 기준, fallback 등으로 12자 초과 시 자르지 않음, 2026-09-01) |

**카테고리**

| 값 | 발생 지점 |
|---|---|
| `APP` | 앱 기동/종료, DLL 로드, 로그 정리 |
| `POS` | 소켓 서버, POS 전문 송수신 |
| `READER` | `ReaderSerial.dll` 연동, 포트 열기/닫기, CALLBACK |
| `VAN` | `KFTC_GIRO.dll`(`FNAISCRDVAN`) 호출 |
| `PAYMENT` | 결제 Flow 오케스트레이션, 큐, 알림창 상태 전이 |
| `KEYDOWN` | 키다운로드 5단계 (§3) |
| `SETTINGS` | 설정 화면 저장/반영 (§2) |
| `UI` | 화면 열기/닫기, 키보드 후킹 |

**코드** — **새 체계를 만들지 않는다.** `E01`(취소) `E02`(Timeout) `E03`(설정화면) `E04`(리더기 미설정)
`E05`(무결성) `E06`(키오스크 고유번호 불일치, §2.3.1 신설) `E99`(내부오류) / `R0x`(리더기 업무
응답코드) `R2x`(리더기 DLL 연동 실패) /
`D0x`(VAN DLL 실패). **POS 응답 전문에 실려 나간 코드와 로그의 코드가 같아야** 장애 신고를 받았을 때
"POS가 받은 코드"로 로그를 바로 찾을 수 있다.

**예시**

고정폭 패딩 반영 예시(2026-09-01, 카테고리 폭8/코드 폭3/거래ID 최소폭12 — 위 렌더링 규칙 참고):

```
[2026-08-31 14:23:01.004] [INFO ] [POS     ] [-  ] [-           ] 결제 요청 수신 — 전문구분=902614
[2026-08-31 14:23:01.010] [INFO ] [PAYMENT ] [-  ] [260831000123] 거래 시작 — 데드라인 100s
[2026-08-31 14:23:04.882] [ERROR] [VAN     ] [D01] [260831000123] FNAISCRDVAN 호출 실패 nRet=-1 retCode=0004
[2026-08-31 14:23:04.890] [INFO ] [POS     ] [D01] [260831000123] 응답 전문 송신 완료
[2026-08-31 14:31:20.117] [INFO ] [APP     ] [-  ] [-           ] 로그 정리 — 90일 초과 3건 삭제
```

거래ID 예시는 SPEC `#9`(요청기관/은행·센터 전문 관리 번호, `AN(12)`, `PosCommonHeader.cs`)와 자릿수를
맞춰 12자리로 표기한다.

기존 `Info(string)` 호출 151곳은 카테고리·코드·거래ID가 전부 `-`인 형태로 그대로 기록된다.
카테고리는 Phase 22 이후 새로 쓰는 로그부터 채우고, 기존 호출을 일괄 개조하지 않는다.

**(c) 거래 상관관계 ID(correlation id)** — 한 결제 거래에서 나온 로그를 서버가 묶어 볼 수 있어야
한다. `PaymentOrchestrator`가 이미 `txId`를 만들어 메시지 문자열에 넣고 있으므로(예:
`$"[PaymentOrchestrator] txId={txId} ..."`), 이것을 **문자열이 아닌 전용 필드로 승격**한다.

값은 `PaymentOrchestrator.LogTxId`가 만드는 것을 그대로 쓴다 — **POS 요청 전문의 `#9` 전문관리번호**,
없으면 `{전문구분}-NOID-{해시}`. 이 값을 쓰는 이유는 **POS(키오스크)가 부여한 번호라서**, 장애 신고가
POS 쪽에서 들어와도 같은 번호로 원캡 로그를 찾을 수 있기 때문이다. 카드정보·개인정보가 아니므로
서버 전송에도 안전하다.

**(d) 최근 N건 인메모리 링버퍼** — 장애 발생 순간에 "직전 무슨 일이 있었는지"를 즉시 첨부해 보낼 수
있도록, 최근 로그(기본 500건)를 메모리에 유지한다. 파일에서 되읽는 방식은 파일 잠금·인코딩 문제가
있어 장애 상황에 쓰기 나쁘다.

**링버퍼에는 렌더링된 문자열이 아니라 구조화된 레코드(시각/레벨/카테고리/코드/거래ID/메시지)를
담는다.** 장래 원격 싱크가 JSON 등으로 보낼 때 텍스트를 정규식으로 되파싱하는 일이 없어야 한다
(파일 싱크만 문자열로 렌더링한다). 링버퍼도 §1.4 마스킹이 이미 적용된 내용만 담는다.

**(e) 전송 시 파일 접근** — 장래 전송 기능이 로그 파일을 읽을 때 기록과 충돌하지 않도록, 파일 열기
모드에 공유 읽기를 허용한다.

### 1.4 마스킹 강제 (필수)

- **로거 진입점에서** 카드번호로 보이는 숫자열(13~19자리 연속 숫자)을 자동으로 마스킹한다.
  앞 6자리 + 뒤 4자리만 남기고 가운데를 `*`로 치환하는 방식을 기본으로 한다.
- 트랙 데이터로 보이는 패턴도 같은 지점에서 차단한다. **PIN 블록은 정규식 마스킹 대상에 넣지
  않는다**(2026-09-01 확정) — PIN 블록은 암호화 데이터 내부에 있고 §1.5 "남기지 않는 것" 규칙상
  로그 메시지에는 애초에 길이만 기록되므로(§3.6), 원문 hex가 로그에 등장할 경로가 실제로 없다.
  대신 16자리 hex 정규식을 두면 이 앱이 실제로 로그에 남기는 `ReaderAuthId`(H/W모델명12+F/W버전4,
  X(16), §1.6)를 오탐해 관측값이 뭉개질 위험이 더 크다.
- 이 처리는 **모든 싱크보다 앞에서** 일어나야 한다 — 파일에는 남고 원격에는 안 가는 식의
  구멍이 생기면 안 된다.
- 마스킹은 방어선이지 면허가 아니다. **호출부에서 카드 데이터를 로그에 넣지 않는다는 원칙은 그대로
  유효하다**(§0.4). Phase 22 완료 시 전수 점검을 다시 수행한다.
- **P22-6(가맹점 설정)·P22-7(관측값 저장) 구현 시 주의**: 전자납부번호(19)·거래금액(18)·
  `ReaderAuthId`(16) 같은 필드는 로그 메시지에 원문으로 넣지 않는다 — 마스커(§1.4)가 자릿수 패턴만
  보고 뭉갤 수 있고, 애초에 §1.5 "남기지 않는 것" 규칙에도 어긋난다.
- **전문 원문 로그(`TelegramLogRedactor`, Phase 22 계획 외 추가 기능) — `#51`(암호화된 비밀번호
  정보) 미마스킹 확정, 재검토 필요**: 902614 전문 원문을 로그에 남길 때 `#46`(암호화된 카드정보)만
  위치 기반으로 부분 마스킹하고 `#51`은 마스킹하지 않는다(2026-09-01 사용자 확정). SEED 암호화가
  아직 구현되지 않아 `#51`에는 지금 평문 PIN이 그대로 들어가므로, **SEED 암호화 구현 전까지는 이
  로그에 실제 고객 PIN이 노출된다.** PIN 암호화 작업 착수 시 반드시 재검토한다 — 자세한 경위는
  `docs/operations/development_plan.md`의 "P22-6부속" 절 참고.

### 1.5 무엇을 남기는가 (기록 기준)

> 현재 151개 호출 지점은 사실상 아래 기준을 이미 따르고 있다. 다만 문서화된 적이 없어 사람마다
> 다르게 판단할 여지가 있었다. 여기서 규칙으로 확정한다.

**대원칙: 통제 밖으로 나가거나 통제 안으로 들어오는 모든 경계에서 한 줄 남긴다.**

원캡이 스스로 하는 계산은 로그가 필요 없다(재현 가능하다). 로그가 필요한 것은 **외부와 맞닿는
지점**이다 — 장애의 원인은 거의 항상 그 경계 너머에 있고, 우리가 볼 수 있는 건 로그뿐이기 때문이다.

| 경계 | 남기는 시점 |
|---|---|
| POS 소켓 | 연결 수락/종료, 요청 전문 수신(전문구분), 응답 전문 송신(결과코드) |
| 리더기 DLL | 명령 송신, 응답/이벤트 CALLBACK 수신, 포트 열기·닫기, 재연결 시도와 그 결과 |
| VAN DLL | `FNAISCRDVAN` 호출 직전, 반환(`nRet`/`retCode`) |
| 사용자 | 취소 버튼, ESC, 설정 저장, 키다운로드 버튼 |
| 앱 수명 | 기동, 종료, DLL 로드, 로그 정리 결과 |
| 거래 수명 | 거래 시작(데드라인), 거래 확정(결과코드와 그 사유) |

**정상 경로도 남긴다.** 오류만 기록하면 장애 분석 때 "실패 직전에 무슨 일이 있었는지"를 알 수 없어
쓸모가 없다. 실패 라인 하나만 있는 로그로는 원인을 못 찾는다.

**레벨 판단 기준**

| 레벨 | 기준 | 예 |
|---|---|---|
| `INFO` | 정상 경로의 경계 통과. 나중에 시간순으로 되짚을 값어치가 있는 사실 | 요청 수신, 거래 시작, 연결 수락, 재연결 성공 |
| `WARN` | 비정상이지만 **처리를 계속했다** — 무시했거나, 복구했거나, 이 건만 버렸다 | 전문 형식 오류(해당 프레임만 폐기), 동시 연결 상한 초과, 포트 에러 감지 후 재연결 |
| `ERROR` | **기능이 실제로 손실됐다** — 거래가 실패했거나, 앱의 일부가 더는 동작하지 않는다 | 리스닝 실패, 수락 루프 종료, DLL 로드 실패, 예상치 못한 예외 |

판단이 애매하면 이렇게 자문한다 — **"이 줄이 ERROR면 새벽에 사람을 깨울 만한가?"** 아니면 `WARN`이다.

**남기지 않는 것 (금지)**

- 카드번호·트랙 데이터·PIN 블록 — §1.4의 마스킹은 최후의 방어선이지, 찍어도 된다는 허가가 아니다.
- **전문 본문 전체.** 전문구분·관리번호·결과코드 등 식별에 필요한 필드만 남긴다.
  **예외**: `TelegramLogRedactor`(§1.4, Phase 22 계획 외 추가)는 POS/VAN 경계에서 전문 원문을
  위치 기반 마스킹만 거쳐 그대로 남긴다 — 이 규칙보다 §1.4의 예외가 우선한다.
- 암호화 데이터·SIGN·HASH 등 긴 바이트열 — **길이만 기록한다**(§3.6).
- 루프 내부의 반복 로그(바이트 단위 수신, 폴링 틱 등). 라운드/시도 단위로만 남긴다.
- 값이 바뀌지 않았는데 주기적으로 찍는 상태 로그.

**분량 감각** — 결제 1건이 대략 10줄(약 2KB)이다. 하루 1,000건이면 2MB/일, 90일 보관 시 180MB
수준으로 키오스크 디스크에 부담이 없다. 이 감각을 크게 벗어나는 로그(거래당 수십 줄)는 위 금지
항목을 어기고 있다는 신호다.

### 1.6 진단 컨텍스트 (장애 보고 봉투)

> 장래의 장애정보 전송 API는 "로그 조각"만으로는 성립하지 않는다. **어느 단말에서 온 보고인지**를
> 함께 실어야 한다. 그 값 중 일부는 **관측했을 때 저장해 두지 않으면 장애 시점에 다시 얻을 수 없다** —
> 로그와 같은 성격이라 이번 범위에서 확보한다.

**저장하지 않는 값** — 보고서를 만드는 시점에 원본에서 그대로 읽는다. 복사해 두면 원본과 어긋날
위험만 생긴다.

| 값 | 원본 |
|---|---|
| 앱 버전 | 어셈블리 |
| OS 버전 | `Environment.OSVersion` |
| VAN Mode (`R`/`OT`/`IT`) | 레지스트리 `TCP\VAN_MODE` (§2.2) |
| COM 포트 구성 | 레지스트리 `SERIALPORT\COMPORT1/2_FIELD` |
| **키오스크 고유번호** | 레지스트리 `TCP\KIOSK_ID` (§2.3) — 설치 시 사람이 입력하는 설정값이다 |

**저장하는 값(관측값)** — 얻을 수 있는 순간이 한정돼 있다.

| 값 | 관측 시점 | 왜 저장해야 하나 |
|---|---|---|
| **리더기 인증 식별 번호** X(16) | `[71]` 상태확인 응답 / 카드리딩 응답 | **리더기 모델을 식별한다** — `H/W모델명(12) + F/W버전(4)`. 장애 대응에 필요한 것은 "어느 개체인지"가 아니라 **"어떤 모델·펌웨어인지"** 다(2026-08-31 확정) |

- **모듈 ID·리더기 이름·리더기 버전·키 버전은 저장하지 않는다**(2026-08-31 확정). 리더기 개체
  고유 식별자는 장애 대응에 필요 없다.
- 두 경로 모두 **파서가 이미 이 값을 추출하고 있다** — `Protocol/Reader/StatusResponseParser.
  ReaderAuthId`, `Protocol/Reader/CardReadResponseParser.ReaderAuthId`. 새로 파싱할 것이 없고,
  저장 지점만 연결하면 된다.
- 리더기 2대 구성이면 포트별로 각각 저장한다(모델이 다를 수 있다).

> `IntegrityCheckStore.PosId`(`"KFTCTAXGIROCAP01"`)는 **모든 단말이 공유하는 하드코딩 상수**라
> 식별에 쓸 수 없다. 신원 키로 착각하지 않는다.

**저장 위치**: 기존 SQLite(`%LOCALAPPDATA%\KFTCTaxGiroCAP\`, `IntegrityCheckStore`와 같은 DB)에
테이블 하나를 추가한다. **레지스트리에 두지 않는다** — 레지스트리는 사용자가 설정한 값을 두는
곳이고, 이것들은 장비·전문에서 관측한 값이라 성격이 다르다. 설정 초기화 때 같이 날아가거나
사용자가 편집 가능한 값처럼 보이면 안 된다.

```
observed_identity
  scope        'COM3' | 'COM4' …   (리더기별 값은 포트를 scope로)
  key          'reader_auth_id'
  value
  observed_at
  PK(scope, key)
```

- **키-값 형태로 둔다** — 장래에 관측 항목이 늘어도 스키마를 바꾸지 않는다.
- **`observed_at`은 필수다.** 보고에 실린 값이 10분 전 것인지 3주 전 것인지에 따라 신뢰도가
  달라진다. 보고 봉투에 값과 관측 시각을 함께 싣는다.
- 관측 시 **upsert**(같은 `scope`+`key`면 덮어쓴다). 이력을 쌓지 않는다 — 필요한 것은 "가장 최근에
  본 값"뿐이다.
- `IntegrityCheckStore`와 동일하게 **모든 공개 메서드가 예외를 밖으로 던지지 않는다**(P11-4).
  진단용 부가 정보를 저장하다가 결제나 키다운로드가 실패하면 본말전도다.
- 리더기 인증 식별 번호는 모델·펌웨어 정보이며 개인정보가 아니다 — 서버 전송에 제약이 없다.

### 2.2 결제 설정 — 금융결제원 서버

**이 설정은 IP/호스트가 아니라 `FNAISCRDVAN`의 첫 인자(Mode)를 고른다**(2026-08-31 확정).

| 표시 문구 | 저장값 | 의미 |
|---|---|---|

| 테스트 서버 | `OT` | 외부망 테스트 |
| 테스트 서버(내부용) | `IT` | 내부망 테스트 |

- **기본값(레지스트리에 값이 없을 때): `R`(운영)** — 2026-08-31 확정.
- 현재 코드는 `Interop/KftcGiroNative.cs`의 `ModeExternalTest = "OT"` 상수를 `VanService.cs:44`가
  쓰고 있다. **이 한 곳을 설정값 주입으로 바꾸는 것이 구현의 전부다.**
- `docs/payment_relay/PRD.md` §10.1의 "VAN Mode는 `OT` 고정" 확정 사항을 **이 PRD로 갱신**한다.
- **포트 번호 항목은 만들지 않는다**(§0.1). 접속지는 `KFTC_GIRO.dll`이 `KFTC_GIROPOS.ini`에서 읽는다.

**검증 방법 — 2026-09-01 사용자 확정**

운영 경로(`App.xaml.cs`)는 아직 `StubVanRelayService`를 꽂고 있어 **평소에는 `FNAISCRDVAN`이 아예
호출되지 않는다**(Phase 20 결정 — VAN 서버가 미개발이라 실제 호출은 무조건 실패). 그래서 "설정을

  되돌린다.**
- 되돌리는 것을 잊으면 모든 실거래가 미개발 VAN을 타서 전부 실패한다 — **원복 확인을 Phase 완료
  조건에 명시적으로 포함한다**(`development_plan.md` P23-8).
- 이 일시 스왑은 Phase 20의 "운영은 Stub 유지" 결정을 바꾸지 않는다. 운영 경로 교체는 VAN 서버가
  준비된 뒤 별도로 판단한다.

### 2.3 결제 설정 — 키오스크 고유번호

| 항목 | 저장 | 기본값 | 검증 |
|---|---|---|---|
| 키오스크 고유번호 | `TCP\KIOSK_ID` (AN 20) | 빈 값 | 20자 이내. **빈 값이면 모든 결제가 거부된다**(§2.3.2, 2026-09-02 재확정 — 반드시 입력해야 하는 필수 항목) |

원본 MFC에 없던 **신규 항목**이다(2026-08-31 추가 확정). 길이 20은 `902614` 전문 `#42`
"키오스크 고유번호"(AN 20)와 맞춘다. **저장 위치는 2026-09-02 `SERIALPORT\KIOSK_ID` →
`TCP\KIOSK_ID`로 재확정**했다(사용자 지시) — 원본 MFC에 없던 신규 항목이라 원본과의 위치 호환
부담이 없으므로, VAN Mode(§2.2)와 같은 `TCP` 하위 키로 모았다.

**왜 필요한가** — 장애 보고에서 **가맹점을 특정하는 유일한 키**인데, 전문으로 받는 값만으로는
부족하기 때문이다. `#42`는 `902614`(승인요청)에만 있고 `501008`·`800000`에는 없다. 따라서
**첫 승인 거래가 일어나기 전까지는 원캡이 자기 신원을 알 수 없다** — 설치 직후 리더기 연결,
포트 설정, 키다운로드처럼 **장애가 가장 자주 나는 구간이 전부 그 이전**이다. 설치 시 사람이
입력해 두면 그 구간의 장애 보고에도 신원이 붙는다.

#### 2.3.1 요청 전문과의 불일치 — 에러 처리

**`902614` 요청의 `#42`가 설정값과 다르면 거래를 거부한다**(2026-08-31 확정).

- 로그만 남기고 넘어가지 않는다. 다른 키오스크의 요청을 받아 처리하고 있다는 뜻이므로 **결제를
  진행하면 안 되는 상황**이다.
- 응답 코드는 기존 3자리 체계에 **`E06`(키오스크 고유번호 불일치)** 를 신설해 쓴다. 원캡 자체
  판단이므로 `E` 계열이 맞다(`PosPaymentResultCode`에 값 1개 추가 →
  `PosResultCodeMapper.ToTelegramCode`에 매핑 1줄 추가).
- 검사는 **카드 리딩 전에** 한다. 리더기를 건드리기 전에 걸러야 사용자가 카드를 대는 헛수고를 막는다.
- 거부 시 `POS` 카테고리 `E06` 코드로 로그를 남긴다. **설정값과 수신값을 둘 다 로그에 적는다** —
  어느 쪽이 잘못됐는지 현장에서 판단해야 한다.

#### 2.3.2 설정이 비어 있을 때

**2026-09-02 재확정(사용자 최종 결정) — 설정값이 비어 있어도 §2.3.1과 동일하게 거부(`E06`)한다.**
과거 버전은 "검증 생략 후 정상 진행"이었으나, 이 결정의 근거였던 "기존 운영 단말이 업데이트되면
값이 비어 있어 결제가 막힌다"는 전제 자체가 **아직 운영 중인 단말이 하나도 없어 성립하지 않는다**
(2026-09-02 확인) — 그래서 굳이 검증을 느슨하게 둘 이유가 없다고 판단해 뒤집었다.

- 설정값이 빈 문자열이면 수신한 `#42`가 무엇이든(빈 문자열이 아닌 이상) 항상 불일치로 간주해
  `E06`을 반환한다. §2.3.1과 완전히 같은 처리(카드 리딩 전 검사, 설정값·수신값을 로그에 함께 남김).
- **구현 방식(2026-09-02 CP2 Opus 리뷰 개선권장 4 반영)** — "빈 값이면 거부"를 문자열 비교
  결과에만 맡기면 성립하지 않는 경우가 있었다: 전문 파서(`PosField.Trim`)가 전체 공백인 필드를
  이미 빈 문자열로 정규화하므로, 설정값도 비어 있으면 "빈 문자열끼리 일치"로 판정되어 오히려
  결제가 **통과**해버리는 loophole이 있었다(설정값 미입력인데 `#42`를 안 보낸 POS 요청이 그대로
  뚫림). 그래서 검사 순서를 **먼저 "설정값 또는 수신값 둘 중 하나라도 빈 문자열이면 값이 같든
  다르든 무조건 `E06`"을 명시적으로 검사하고, 그 다음에야 `Ordinal` 문자열 비교로 일치 여부를
  판단한다**(양쪽 `TrimEnd()` 이후 기준). 이 순서 덕분에 "빈 값이면 모든 결제가 거부된다"가
  문자 그대로 성립한다 — 수신값이 빈 문자열로 오는 경우(SPEC상 `#42`를 안 채우는 경우, 원본이
  전체 공백인 경우 등)까지 전부 포함해서다.
- 이 정책은 **키오스크 고유번호를 반드시 설치 시점에 입력해야 한다**는 뜻이 된다 — 입력하지 않은
  상태로는 결제 자체가 되지 않는다. 장래에 실제 운영 단말이 생겨 이 항목 없이 이미 배포된 단말이
  나타나면, 이 결정을 다시 재검토해야 한다(그 경우를 대비해 과거 버전의 논리를 이 절 히스토리로
  남겨 둔다 — 아래 참고).
- 수신한 `#42`를 **레지스트리에 자동으로 써넣지 않는다** — §2.3.1과 동일 이유(사용자 설정을
  프로그램이 몰래 바꾸면 검증이 무의미해진다).

> **과거 버전(2026-08-31~2026-09-02, 폐기됨)**: "검증을 수행하지 않고 거래를 정상 진행한다 — 이
> 항목이 신규라서 기존 운영 단말이 업데이트되면 값이 비어 있고, 그 상태에서 거래를 막으면 결제가
> 전면 중단되기 때문"이었다. 빈 값일 때는 `WARN` 로그만 남기고 장애 보고 봉투에는 "미식별"로
> 나갔다(§1.6.1). 이 논리는 여전히 유효한 우려이므로, 실제 운영 단말이 생기는 시점에 재검토가
> 필요하다.

### 3.2 전체 흐름

`암호화리더기설계서_20250122.pdf` §1.11 "키 다운 프로세스"가 정본이다. 원캡은 **리더기와 서버 사이의
릴레이**이며, 5번의 왕복으로 끝난다.

```
① 원캡 → 리더기    [63] 키 다운로드 시작 요청      → [73] 응답 (키버전 + 모듈ID 획득)
② 원캡 → 서버      상호인증 요청 (ISO 0100)        → 응답 (0110)  ※ FNAISCRDVAN
③ 원캡 → 리더기    [64] 키 다운로드 상호인증 요청  → [74] 응답 (암호화 데이터 획득)
④ 원캡 → 서버      Key Bundling 요청 (ISO 0120)    → 응답 (0130)  ※ FNAISCRDVAN
⑤ 원캡 → 리더기    [65] Using Key 전송 요청        → [75] 응답 (완료)
```

### 3.3 원캡은 암호 연산을 하지 않는다 (중요)

RSA2048 서명 검증, AES128 암·복호화, SHA256 해시, DUKPT 키 파생은 **전부 리더기와 서버가
수행한다.** 원캡이 하는 일은 **한쪽에서 받은 바이트열을 잘라 다른 쪽 전문에 붙이는 것뿐**이다.
아래 표가 그것을 바이트 단위로 보여준다 — 길이가 정확히 맞아떨어진다.

| 단계 | 받는 곳 | 받는 데이터 | 보내는 곳 | 보내는 데이터 |
|---|---|---|---|---|
| ② 요청 | 리더기 `[73]` | 키버전(2) + 모듈ID(10) | 서버 `0100` P-28 | **AN 12** = 키버전(2) + 모듈ID(10) |
| ③ 요청 | 서버 `0110` P-28 | **AN 610** = 키버전(2) + HASH(64) + RND(32) + SIGN(512) | 리더기 `[64]` | HASH(64) + RND(32) + SIGN(512) = **608** |
| ④ 요청 | 리더기 `[74]` | 키버전(2) + … + 모듈ID(10) + 암호화데이터(512) | 서버 `0120` P-29 | **AN 524** = 키버전(2) + 모듈ID(10) + 암호화데이터(512) |
| ⑤ 요청 | 서버 `0130` P-29 | **AN 146** = 키버전(2) + 암호화데이터(144) | 리더기 `[65]` | 암호화데이터(128) + MAC(16) = **144** |

즉 ③과 ⑤에서는 서버 응답의 앞 2바이트(키버전)를 떼고 나머지를 그대로 리더기에 넘기며, ②와 ④에서는
리더기 응답에서 필요한 필드만 골라 붙인다. **`System.Security.Cryptography`를 쓸 일이 없다.**

### 3.4 리더기 구간 전문 상세

`ReaderSerial.dll`의 `Reader_SendCommand(readerId, commandCode, data, dataLength)`에 아래 `data`만
넘긴다. STX / Data 길이 / ETX / LRC는 **DLL이 처리하므로 직접 만들지 않는다.** 응답 `data`는
업무 응답 코드 2바이트로 시작한다(`API명세서.md` §9).

**[63] 키 다운로드 시작 요청** — 요청 데이터 없음(`dataLength = 0`)

**[73] 키 다운로드 시작 응답**

| 필드 | 속성 | 비고 |
|---|---|---|
| 응답 코드 | X(2) | `"00"`이 아니면 실패 — §3.6 |
| 키 버전 | X(2) | IPEK 버전2 |
| 리더기 이름 | X(16) | Space 우측 패딩 |
| 리더기 버전 | X(16) | Space 우측 패딩 |
| 모듈 ID | X(10) | 모델코드(3) + IPEK버전1(1) + Y(1) + M(1, 16진 표기) + ####(4) |

**[64] 키 다운로드 상호 인증 요청**

| 필드 | 속성 | 비고 |
|---|---|---|
| HASH | X(64) | RND의 SHA256 해시값, 2byte expanding(hex→ascii) |
| RND | X(32) | 서버가 생성한 랜덤값 |
| SIGN | X(512) | SK(man)으로 RND를 sign한 값 |

**[74] 키 다운로드 상호 인증 응답** — 응답코드(2) + 키버전(2) + 리더기이름(16) + 리더기버전(16) +
모듈ID(10) + **암호화 데이터 X(512)**

**[65] Using Key 전송 요청** — 암호화 데이터 X(128) + MAC 값 X(16)

**[75] Using Key 전송 응답** — 응답코드(2) + 모듈ID(10)

> **SPEC 표기 참고**: `[65]` 전문 표만 `LRC`가 `ETX`보다 먼저 적혀 있는데, 다른 모든 전문은
> `ETX` → `LRC` 순이다. 오타로 판단한다. 프레임 조립은 DLL이 하므로 구현에는 영향이 없다.

**IPEK 버전 관리**(설계서 §3.4 각주) — 키 다운로드 시 IPEK 버전2가 먼저 `"00"`~`"FF"`로 증가하고,
`"FF"` 이후 다시 수행하면 IPEK 버전1이 `'0'`~`'F'`로 증가한다. 둘 다 최대치가 되면 더 증가하지 않고
**해당 버전으로 거래하면 서버가 거절(`395`, 단말기 교체 요망)** 한다. 원캡은 이 값을 해석하지 않고
그대로 전달하지만, 서버가 `395`를 주면 사용자에게 "단말기 교체가 필요합니다"로 안내해야 한다.

리더기 응답 코드는 `암호화리더기설계서` §2.2 표를 따른다. 키다운로드에 직접 관련된 코드는 다음과 같다.

| 코드 | 의미 | 설명 |
|---|---|---|
| `00` | 정상 | |
| `10` | 상호인증오류 | Key 상호인증 시 |
| `11` | 암호화/복호화오류 | Key 다운로드 시 |

  단말 상태를 바꾸는 조작이라 실패 후 무턱대고 반복하면 IPEK 버전만 소모될 수 있다.
- 실패 문구에는 **어느 단계에서 실패했는지**를 담는다(예: "키다운로드 실패 — 상호인증 단계, 리더기
  응답코드 10"). 단계·코드가 없으면 현장 대응이 불가능하다.
- 서버 통신 실패(`FNAISCRDVAN`의 `nRet != 0`)는 결제와 같은 `D0x` 분류를 쓴다.
- 모든 단계의 시작·응답을 **`KEYDOWN` 카테고리로 로그에 남긴다**(§1.3). **리더기 구간**([64]/[65]/[74],
  `ReaderService`/`KeyDownloadService`)은 응답 데이터 본문(SIGN, 암호화 데이터 등)을 길이만 기록하고
  내용은 남기지 않는다. **VAN 서버 구간**(0100/0110/0120/0130, `KeyDownloadVanClient`)은
  2026-09-02 사용자 명시적 확정(위험 고지 후 재확인)으로 이 규칙의 예외다 — 결제 경로(`VanService`)와
  동일하게 요청/응답 전문 전체를 마스킹 없이 그대로 로그에 남긴다. SIGN(512)/HASH(64)/RND(32)/
  암호화데이터가 전문 대부분을 차지하므로 사실상 키 자재가 로그 파일에 평문으로 남는다는 뜻이지만,
  사용자가 그 위험을 인지한 뒤 그대로 진행하기로 했다. 지금은 위치 기반 마스킹 없이 전체를 남기되,
  나중에 특정 필드를 마스킹할 필요가 생기면 `TelegramLogRedactor`(POS/VAN 결제 경계, §1.4)처럼
  위치 기반 마스킹을 추가하는 방식으로 간다 — 지금 당장 마스킹 로직을 구현할 필요는 없다.

## §4 카드정보 메모리 클리어 (Phase 25)

### 4.1 왜 하는가 — 인증 시험 기준

**2026-09-03 사용자가 인증 시험 기관으로부터 받은 안내가 이 절의 유일한 근거다**(별도 기준 문서를
확보하지 못했다 — 문구를 임의로 확대·축소 해석하지 않는다).

> 현재 적용 중인 시험 기준에서는 메모리에 저장된 민감정보에 대해 DoD 방식에 따른 3회
> 덮어쓰기(Overwrite)를 요구하고 있습니다. 다만 관련 기준이 개정될 예정으로, 시험 신청 시점에 따라
> 적용되는 삭제 방법이 달라질 수 있습니다.
>
> 개정 예정인 기준에서는 거래 승인에 사용된 민감한 신용카드 정보를 다음 절차에 따라 메모리에서
> 완전 삭제하도록 하고 있습니다. ① 0 등의 특정 문자로 덮어쓰기(Overwrite) ② 메모리 할당 해제 또는
> Garbage Collector(GC) 호출
>
> 따라서 C#에서는 카드정보를 가급적 string과 같이 직접 값을 변경하기 어려운 형태보다는 byte[],
> char[] 등 명시적으로 덮어쓰기가 가능한 형태로 관리하고, 사용 완료 후 해당 메모리 영역을 덮어쓴 후
> 메모리 할당 해제 또는 GC가 이루어지도록 구현하는 것을 권고드립니다.

여기서 뽑아내는 요구사항은 셋이다.

1. **타입** — 카드정보를 `string`이 아니라 **명시적으로 덮어쓸 수 있는 `byte[]`/`char[]`** 로 관리한다.
2. **덮어쓰기** — 사용 완료 후 덮어쓴다. 현행 기준은 3회, 개정 예정 기준은 "0 등 특정 문자로" 1회.
3. **해제** — 덮어쓴 뒤 **할당 해제 또는 GC가 이루어지도록** 한다.

**기준 해석 — 2026-09-03 사용자 확정**

- 개정 후 기준(1회)은 개정 전 기준(3회)의 부분집합이다. **3회로 구현하면 양쪽 모두 충족**하며,
  나중에 개정 기준이 적용돼도 코드 구조를 바꿀 필요 없이 횟수 상수만 줄이면 된다. → **3회로 간다.**
- ②의 "GC가 이루어지도록"은 **`GC.Collect()` 강제 호출을 요구하는 것이 아니다.** 덮어쓴 뒤 참조를
  끊어 GC가 회수하도록 두면 충족된다. 결제 건마다 `GC.Collect()`를 부르면 힙 전체를 훑느라 수십 ms가
  튀므로 **강제 호출은 하지 않는다.**
- 기준은 **"사용 완료 후"** 삭제를 요구한다 — 거래가 진행 중인 동안 카드정보가 메모리에 있는 것은
  "사용 중"이므로 기준 위반이 아니다. 이 해석이 §4.3.3(클리어 시점) 선택의 근거다.

### 4.3 구현 방침 (2026-09-03 확정)

#### 4.3.1 `SecureClear` 헬퍼 — 덮어쓰기의 유일한 지점

민감 버퍼를 지우는 방법은 **한 곳으로 모은다.** 호출부가 직접 `Array.Clear`를 부르지 않는다.

- 덮어쓰기 **3회**, **마지막 패스는 `0x00`** 으로 끝낸다(예: `0x00` → `0xFF` → `0x00`). 마지막을 0으로
  끝내야 개정 기준의 "0 등의 특정 문자로 덮어쓰기" 문구까지 그대로 만족한다.
- 횟수는 **상수 하나**로 둔다 — 기준이 1회로 완화되면 이 상수만 바꾼다(호출부 무변경).
- `byte[]`와 `char[]` 두 오버로드를 제공한다.
- `null`/빈 배열을 받아도 무해하게 통과한다(호출부에 조건 분기를 만들지 않기 위함 —
  `KeyDownloadVanClient`가 이미 쓰는 방식).
- **`GC.Collect()`는 부르지 않는다**(§4.1). 덮어쓴 뒤 참조를 끊는 것으로 갈음한다.

#### 4.3.2 타입 변경 — `string` → `char[]`/`byte[]`

**범위: 결제 Flow 전체**(2026-09-03 사용자 확정). 카드리딩 콜백 → `CardReadData` →
`PaymentOrchestrator`(POS/VAN 전문 조립) → `PinFieldEncoder` → POS 응답까지 이어지는 경로에서
민감정보를 나르는 `string`을 전부 바꾼다.

- **대상 필드는 `CardReadData` 19개 전부 + PIN**(2026-09-03 사용자 확정). 필드별로 "이건 민감한가"를
  판단하지 않는다 — 판단이 들어가는 순간 누락 위험이 생기고, 심사에서 "이 필드는 왜 안 지우느냐"를
  설명해야 한다. 거래구분·키버전·TC·모듈ID·리더기고유번호까지 일괄 대상이다.
- `string`은 불변이라 **덮어쓰기가 원천적으로 불가능**하다. 타입을 바꾸지 않으면 §4.1의 요구사항 1·2를
  어떤 방법으로도 만족시킬 수 없다 — 이 Phase에서 타입 변경은 선택이 아니라 전제다.

#### 4.3.3 클리어 시점 — 하이브리드

| 대상 | 시점 | 근거 |
|---|---|---|
| **임시 버퍼** — §4.2의 #1, #2, #8, #9, #10, #12, #13 | 만든 메서드 안에서 `try/finally`로 **즉시** | 한 메서드 안에서 생성·소비되고 끝나므로 수명이 눈에 보인다. 판단이 필요 없어 회귀 위험이 사실상 없고, 거래 종료 시점에는 이미 스코프를 벗어나 참조가 없어 일괄 클리어로는 **구조적으로 손댈 수 없다** |
| **거래가 들고 있는 주요 데이터** — §4.2의 #3~#7, #11 | 거래 1건 종료 시 `finally`에서 **일괄** | 거래 도중 계속 필요하므로 조기 클리어가 불가능하다. `finally`이므로 정상 종료·예외·타임아웃·POS 연결 끊김·조기 return을 모두 통과한다 |

원칙 한 줄로: **"각 데이터를 더 이상 필요 없어지는 가장 이른 시점에 지운다."**

**왜 "전부 즉시"가 아닌가** — 주요 데이터까지 단계마다 즉시 지우려면 필드마다 "마지막으로 쓰이는
지점이 정확히 어디냐"를 판단해야 하고, 하나만 틀려도 **이미 실거래 검증이 끝난 결제 Flow가 깨진다.**
§4.1의 해석대로 거래 진행 중 보유는 기준 위반이 아니므로, 노출 시간 수백 ms를 줄이자고 회귀 위험을
지지 않는다.

**왜 "전부 일괄"이 아닌가** — 위 표의 임시 버퍼를 커버할 수 없다(참조가 이미 없다).

#### 4.3.4 해제

덮어쓴 직후 참조를 끊어 GC가 회수하도록 둔다. `GC.Collect()` 강제 호출은 하지 않는다(§4.1).

#### 4.3.5 Phase 24 키다운로드 경로 소급 적용

키다운로드가 이미 쓰고 있는 `Array.Clear`(1회 0 채우기)를 **§4.3.1의 `SecureClear`로 교체한다**
(2026-09-03 사용자 확정). 인증 기준이 명시하는 대상은 "신용카드 정보"라 키 정보는 문언상 대상이
아니지만, **프로젝트 안에 덮어쓰기 방식이 두 가지 존재하는 상태를 만들지 않는다** — 심사 대응과 코드
일관성 양쪽에서 손해다. 호출부 구조는 그대로 두고 호출 대상만 바꾸는 변경이라 Phase 24의 검증
결과에 미치는 영향이 작다.

### 4.4 알려진 한계 (숨기지 않고 명시한다)

이 방침으로도 지워지지 않는 것이 있다. 심사에서 질문이 나올 수 있으므로 미리 적어 둔다.

1. **GC 세대 압축(compaction) 복사본** — managed 배열은 GC가 힙을 정리하며 다른 주소로 **복사**할 수
   있다. 그런 일이 있었다면 우리가 덮어쓰는 것은 새 위치뿐이고 **옛 위치의 내용은 남는다.** 덮어쓰기를
   몇 회 하든 이 복사본은 지울 수 없다.
   → 해결하려면 해당 버퍼를 `GCHandle`로 **pin** 하거나 unmanaged 메모리(`Marshal.AllocHGlobal` →
   덮어쓰기 → `FreeHGlobal`)로 옮겨야 한다. **이번 범위에서는 하지 않는다** — 인증 기준이 요구하는
   사항이 아니고(문구는 덮어쓰기와 해제/GC만 말한다) 모든 사용처를 래퍼 경유로 바꾸는 큰 변경이다.
   심사에서 지적받으면 그때 해당 필드만 pin 처리한다.
2. **프로세스 강제 종료·크래시** — 클리어 코드가 실행되지 못한다. 어떤 시점 선택으로도 막을 수 없다.
3. **`string`으로 남는 잔재** — §4.3.2의 타입 변경 범위 밖(로그 문자열, 화면 표시용 마스킹 문자열 등)에
   민감정보가 흘러 들어가면 그것은 지울 수 없다. 그래서 §4.5의 로그 점검을 함께 한다.
4. **`net48` 제약** — `CryptographicOperations.ZeroMemory`가 없다(.NET Core 3.0+). 직접 구현한
   `SecureClear`로 대체한다. 다만 JIT가 "결과를 읽지 않는 쓰기"로 보고 덮어쓰기를 제거할 이론적
   가능성이 있으므로, 최적화에 지워지지 않도록 구현한다(구현 방법은 Phase 25 착수 시 확정하고
   Release 빌드 실측으로 확인한다).

### 4.5 로그 현황 점검 (이번 범위: 점검하고 기록까지)

2026-09-03 사용자 확정 — **로그는 이번 Phase에서 구조를 바꾸지 않는다. 현황을 전수 점검해 이 절에
표로 기록하고, 문제가 발견된 곳만 수정한다.** 인증 기준이 말하는 것은 "메모리"이고 로그 마스킹은 이미
§1.4가 다루기 때문이다.

착수 시점에 확인된 사실:

- `LogRingBuffer`는 **최근 500건의 로그 레코드를 메모리에 상주**시킨다(Phase 22 P22-4). 로그 문자열에
  민감정보가 들어가면 그 문자열은 링버퍼가 밀어낼 때까지 메모리에 남고, `string`이라 덮어쓸 수 없다.
- 결제 경로의 POS/VAN 전문 로그는 `TelegramLogRedactor`가 **`#46`(암호화 카드데이터)만 마스킹**한다.
  `#51`(PIN)은 `PosResponseTelegram.BuildFailure`가 응답에서 비우지만, 요청 로그 쪽 처리는 착수 시
  재확인한다.
- 키다운로드 VAN 서버 구간(0100/0110/0120/0130)은 **마스킹 없이 원문 전체**를 남긴다(§3.6, 사용자
  확정). 카드정보는 아니지만 키 전송 페이로드가 그대로 남는다 — 이 절의 점검 표에 사실대로 기록한다.

**Phase 25에서 할 일**: 위 세 가지를 포함해 민감정보가 로그 문자열로 흘러가는 경로를 전수 점검하고
결과를 표로 남긴다. 마스킹 누락이 발견되면 그곳만 고친다.

### 4.6 검증 — 심사 증적

2026-09-03 사용자 확정 — **진단 하네스와 문서를 모두 만든다.**

- **진단 하네스**: 기존 `--payment-flow-test` / `--keydown-test`와 같은 방식의 CLI 진단 모드를 추가해,
  민감 버퍼가 클리어된 뒤 **실제로 내용이 남아 있지 않은지 읽어서 확인**하고 결과를 로그로 남긴다.
  심사에서 실증을 요구받으면 이 하네스를 그대로 돌린다.
- **문서**: §4.2 표(어디에 무엇이 있는가)와 §4.3.3 표(무엇을 언제 지우는가), §4.4(한계)를 심사 답변
  자료로 그대로 쓸 수 있게 유지한다.
- **실장비 검증 포함**(사용자 확정) — 타입 변경이 이미 실거래 검증을 마친 결제 Flow 전체를 건드리므로,
  하네스만으로는 회귀를 다 잡을 수 없다. Phase 24와 같이 실장비로 결제를 끝까지 돌려 확인한다.
- **Opus 다회 리뷰 루프 적용**(사용자 확정) — dev 구현 → Opus 전체 검증 → 수정 → 재검증 반복.
  Phase 24에서 "개선권장을 고치는 리팩터링이 새 치명적 회귀를 만든" 전례가 있으므로, 검증은 수정한
  부분만이 아니라 **결제 Flow 전체 로직**을 대상으로 한다.

### 4.7 이번 범위에서 하지 않는 것

- `GCHandle` pin / unmanaged 버퍼 전환(§4.4 #1) — 기준이 요구하지 않는다. 필요해지면 별도 Phase.
- `GC.Collect()` 강제 호출(§4.1).
- 로그 구조 변경(§4.5) — 점검과 기록, 발견된 누락 수정까지만.
- 레지스트리·파일에 **저장된** 데이터의 삭제 — 이 기준은 메모리에 관한 것이다. 애초에 이 앱은 카드정보를
  디스크에 저장하지 않는다(§3.1 "로컬 이력 없음"과 같은 원칙).
