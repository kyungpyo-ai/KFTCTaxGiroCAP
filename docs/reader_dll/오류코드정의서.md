## 2. 두 체계의 구분 (중요)

이 DLL이 다루는 "오류/결과 코드"는 서로 완전히 다른 두 체계로 나뉜다. 절대 섞어서 해석하면 안 된다.

| 구분 | `ReaderResult` (본 문서의 대상) | SPEC 업무 응답 코드 |
|---|---|---|
| 정의 위치 | `src/ReaderSerial/ReaderErrors.h` | `src/ReaderSerial/CommandCodes.h` 하단 "P7-4" 부록 주석 (SPEC §2.2 원문) |
| 값의 범위/형식 | `int`, 음수(`READER_OK`만 0), 4byte 정수 | `00`~`23`, **ASCII 2byte 문자열**(예: `'0'` `'0'`) |
| 누가 정하는가 | 이 DLL 자체가 정의 | 리더기 제조사의 SPEC 문서 |
| 어디로 전달되는가 | `Reader_OpenPort`/`Reader_ClosePort`/`Reader_IsPortOpen`/`Reader_SendCommand`의 **함수 반환값** | `READER_CALLBACK`의 **`data` 파라미터 첫 2byte** (응답 Data 영역 내부) |
| DLL의 해석 여부 | DLL 자신이 발생시키고 의미를 정의함 | DLL은 이 값을 해석하지 않고 그대로 전달만 함(pass-through) |
| 의미 예시 | "포트가 이미 열려 있다", "명령 처리 중 BUSY 상태다" 등 **통신/DLL 레벨** 오류 | "IC 카드 거래 불가", "사용자 취소" 등 **리더기 업무 레벨** 결과 |

SPEC 업무 응답 코드 `00`~`23` 전체 표는 `DOC/개발문서/API명세서.md` §9 및 `src/ReaderSerial/CommandCodes.h` 하단 주석을 참조한다(이 문서에서는 중복 기재하지 않는다).

**`READER_CALLBACK`의 `eventType`(`ReaderEventType`)은 위 두 체계와도 또 다른, 세 번째 값이다** — `ReaderResult`처럼 이 DLL이 정의하지만, 전달 위치와 값의 범위가 다르다(`eventType`은 CALLBACK 전용 파라미터, 값은 `0`~`5`의 작은 양수). `ReaderEventType` 자체의 정의는 `DOC/개발문서/API명세서.md` §8을 참조한다 — 이 문서(`ReaderResult`)와는 별개 문서/별개 섹션에서 다룬다. **2026-08-13부터 이 둘 사이에는 더 이상 대응하는 `ReaderResult` 값 자체가 없다** — `READER_EVENT_TIMEOUT`/`LRC_ERROR`/`RECEIVE_ERROR`/`FRAME_STALL`이 예전에 논리적으로 대응시켰던 `READER_ERR_TIMEOUT`/`LRC_MISMATCH`/`RECEIVE_FAIL`/`FRAME_STALL`은 죽은 값으로 확인되어 제거됐다(§3.4/§3.5 참조) — 이 상황들은 이제 `eventType` 하나로만 식별한다.

### 3.7 핀패드 계열 (-1400, 2차 개발, 2026-08-12 추가 제거)

`Pinpad_SendCommand`의 반환값으로 전달된다. §2의 "누가 정하는가/DLL의 해석 여부" 구분과 동일하게, 이 값 자체는 이 DLL이 정의한 통신/시퀀스 레벨 결과이며 SPEC 업무 응답 코드(00~23)와는 다른 체계다.

**2026-08-12 갱신 — `PINPAD_CALLBACK` 전면 재설계 + 죽은 값 2개 추가 제거**: `PINPAD_CALLBACK` 시그니처가 전면 재설계되어(`DOC/개발문서/API명세서.md` §11 참조) 3번째 파라미터가 `result`(`ReaderResult`)에서 `commandCode`(`PinpadCommandCode`)로 바뀌었다. 이 재설계로 `PINPAD_CALLBACK`이 실어 보내던 `failInfo`(3byte: fc/subCode/reason) payload와 `PinpadFailReason`(내부 전용 enum) 개념은 완전히 제거됐다 — 실패 원인은 이제 `PinpadEventType`(§3.7-1 표, 8종 이벤트로 세분화) 자체가 표현한다. 그 결과 `READER_ERR_PINPAD_STEP_FAILED`(-1401)/`READER_ERR_PINPAD_TIMEOUT`(-1402)도 `Pinpad_SendCommand`가 실제로 반환하는 값이 아니게 되어(반환 경로가 완전히 사라짐) **`ReaderErrors.h`에서 제거했다** — 뒤에 남은 값이 없으므로 결번 처리 없이 그냥 제거했고 재번호도 불필요하다(2026-08-05/2026-08-11과 동일한 논리, `package/` 미배포).

**2026-08-11 재번호(역사적 기록)**: 최초 정의된 -1400~-1406 범위 중 코드상 어디서도 발생하지 않던 죽은 값 3종(`READER_ERR_PINPAD_NAK`=-1402, `READER_ERR_PINPAD_TAMPER`=-1403, `READER_ERR_FRAME_AMBIGUOUS`=-1405 — NAK/Tamper는 애초부터 `READER_ERR_PINPAD_STEP_FAILED`로 흡수되어 있었고, `FRAME_AMBIGUOUS`는 2026-08-10 `FrameDispatcher.cpp` 재설계로 도달 불가능해졌음)를 제거하고 남은 3개를 -1400~-1402로 빈틈없이 재번호했었다(그 -1401/-1402가 바로 위 2026-08-12 항목에서 추가로 제거된 값이다).

| 값 | 이름 | 의미 | 발생 상황(코드 근거) |
|---:|---|---|---|
| -1400 | `READER_ERR_PINPAD_NOT_SUPPORTED` | 이 포트에 `pinpadCallback`이 등록되지 않음 | `Pinpad_SendCommand`: `ctx->pinpadCallback == nullptr`(`ReaderApi.cpp:406,409`) — 타임아웃 대기 없이 즉시 반환 |

**참고 — `Pinpad_SendCommand`가 반환하는 값은 -1400 하나가 아니다**: `Pinpad_SendCommand`는 `READER_ERR_INVALID_READER_ID`(-1003)/`READER_ERR_PORT_NOT_OPEN`(-1103)/`READER_ERR_INVALID_ARGUMENT`(-1001)/`READER_ERR_BUSY`(-1004)도 반환하고, 프레임 빌드/물리 송신 인프라를 `Reader_SendCommand`와 공유하는 탓에 `READER_ERR_INVALID_LENGTH`(-1300, §3.5)/`READER_ERR_BUFFER_OVERFLOW`(-1301, §3.5)/`READER_ERR_PORT_CLOSING`(-1105, §3.3)/`READER_ERR_SEND_FAIL`(-1200, §3.4)도 반환할 수 있다(2026-08-13 확인, 각 항목의 "발생 상황" 열 참조). `Pinpad_SendCommand`가 반환 가능한 값의 전체 목록은 `API명세서.md` §10 표가 정본이다 — 이 -1400 값은 핀패드에서만 나오는 **추가** 값일 뿐이다.

과거 -1401(`READER_ERR_PINPAD_STEP_FAILED`)/-1402(`READER_ERR_PINPAD_TIMEOUT`)는 2026-08-12 `PINPAD_CALLBACK` 재설계로 제거됐다(위 갱신 문단 참조). 과거 -1404(`READER_ERR_PINPAD_NO_INPUT`, 고객 미입력 전용 코드 — 0xF7 단계 NAK를 -1401로 통합하며 2026-08-11 제거)는 2026-08-11 재번호 이전에 이미 결번이었다. 이 값들 모두 더 이상 참조할 필요가 없다.

#### 3.7-1 `PinpadEventType`(`PINPAD_CALLBACK`의 `eventType`) — 실패 원인별 값

2026-08-12부터 `PINPAD_CALLBACK`으로 전달되는 실패 정보는 위 `ReaderResult` 값이 아니라 `PinpadEventType`(공개 헤더 `ReaderSerial.h`) 값 자체다 — 리더기 `ReaderEventType`과 동일하게, 원인마다 최상위 이벤트로 승격되어 있다. 전체 표/각 원인의 상세 발생 조건은 `DOC/개발문서/API명세서.md` §12를 정본으로 한다.

| `PinpadEventType` 값 | 대응하는 과거 `PinpadFailReason`(폐지됨) |
|---|---|
| `PINPAD_EVENT_TIMEOUT` (1) | 과거 `PINPAD_FAIL_TIMEOUT` (0x01) |
| `PINPAD_EVENT_NAK` (2) | 과거 `PINPAD_FAIL_NAK` (0x02) |
| `PINPAD_EVENT_LRC_ERROR` (3) | 과거 `PINPAD_FAIL_LRC` (0x03) |
| `PINPAD_EVENT_TAMPER` (4) | 과거 `PINPAD_FAIL_TAMPER` (0x04) |
| `PINPAD_EVENT_SEND_FAIL` (5) | 과거 `PINPAD_FAIL_SEND` (0x05) |
| `PINPAD_EVENT_RECEIVE_ERROR` (6) | 과거 `PINPAD_FAIL_RECEIVE_ERROR` (0x06, 2026-08-12 추가) |
| `PINPAD_EVENT_FRAME_STALL` (7) | 과거 `PINPAD_FAIL_FRAME_STALL` (0x07, 2026-08-12 추가) |

값이 우연히 대응(예: `PINPAD_EVENT_TIMEOUT = 1`이 옛 `PINPAD_FAIL_TIMEOUT = 0x01`과 같음)하는 것은 두 enum 모두 선언 순서대로 번호가 매겨졌기 때문일 뿐, 코드에 하드코딩할 만한 의미 있는 매핑은 아니다.

## 4. PRD §9 원표와의 대조 결과

`DOC/개발문서/PRD.md` §9의 `ReaderResult` enum 원문과 `src/ReaderSerial/ReaderErrors.h`를 1:1 대조한 결과는 다음과 같다.

- **값/이름 자체는 2026-08-05 재번호 이후로는 계속 일치해왔으나, 2026-08-13부터 다시 어긋난다** — PRD §9 원표는 최초 요구사항 스냅샷으로 취급해 이후 코드 변경 때마다 고쳐 쓰지 않는 것이 이 프로젝트의 관례이므로, PRD.md §9에는 여전히 `READER_ERR_RECEIVE_FAIL`/`READER_ERR_TIMEOUT`/`READER_ERR_FRAME_STALL`/`READER_ERR_LRC_MISMATCH`(구 -1301)가 남아 있다. 실제 `ReaderErrors.h`에는 이 4개가 없다 — [^3] 참조. 이 문서(오류코드정의서.md) §3이 코드 기준 정본이다.
- **`READER_ERR_FRAME_STALL = -1203`은 원래 PRD §9 원표에 없던 값이었으나, 2026-08-05 재번호 시 PRD §9 원표도 함께 갱신되어 그때는 양쪽에 동일하게 존재했다.** Phase 9(P9-9, Inter-byte Timeout 감지, 2026-07-30)에서 사용자 확정으로 코드에 먼저 추가됐던 값이다. **2026-08-13에 이 값 자체가 죽은 값으로 확인되어 코드에서 제거됐다** — 바로 위 항목 참조.
- 그 외 `-1001`~`-1900` 범위의 값 순서/그룹핑(인자·명령 상태 / 포트 상태 / 송수신 / 프레임 구성 / 내부)도 PRD §9 원문 순서와 동일하다.

[^1]: 2026-08-05 재번호 작업 이전에는 `READER_ERR_PORT_CLOSED`(-1105), `READER_ERR_FRAME_BUILD_FAIL`(-1299), `READER_ERR_INVALID_FRAME`(-1300), `READER_ERR_UNEXPECTED_RESPONSE`(-1304) 4개 값이 `ReaderErrors.h`와 PRD §9 원표에 선언은 되어 있었지만, `src/ReaderSerial` 전체를 grep한 결과 이 값들을 실제로 반환하는 코드 경로가 하나도 없었다(2026-08-03 확인). 각 값이 다루려던 상황은 실제로는 더 구체적인 다른 코드(`READER_ERR_PORT_NOT_OPEN`, `READER_ERR_INVALID_ARGUMENT`/`INVALID_LENGTH`/`BUFFER_OVERFLOW`, `READER_ERR_LRC_MISMATCH`, 또는 CALLBACK 자체를 생략하는 방식)로 흡수되어 처리되고 있었다. 2026-08-05 재번호 작업에서 이 4개 죽은 값은 `ReaderResult` enum 자체에서 완전히 제거됐다 — 이제 이 값들은 존재하지 않으며, POS 개발자가 이에 대한 분기를 준비할 필요가 없다.
