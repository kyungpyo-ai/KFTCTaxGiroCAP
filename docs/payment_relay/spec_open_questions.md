# POS-원캡 SPEC 미기재 항목 확정 기록

> **이 문서는 정본이 아니다.** POS↔원캡 전산설계서(SPEC)는 **우리(KFTC/원캡) 측이 직접 작성·수정하는
> 문서**다(외부 발주처에 보낼 질의 대장이 아니다 — 2026-09-22 정정, 이전 판까지 "발주처 질의"로 잘못
> 표기돼 있었다). 이 문서는 **SPEC 원문에 명문 지시가 없어 구현 시 별도 확정이 필요했던 항목**을
> 모아 두는 기록이다. 아래 매핑표는 **조사 기록**이며, 등급 (다)/(라) 행은 SPEC 원문 명문이 아니라
> 확정된 구현 근거임을 표시한다.
>
> **SPEC 문서 자체를 우리가 고칠 수 있으므로**, 여기 확정된 값 중 SPEC에 명문으로 실어 두는 게 나을
> 항목은 다음 SPEC 개정 때 반영할 수 있다(아직 반영 여부 미정 — §4 "SPEC 반영" 열 참고).
>
> **왜 별도 문서인가** — 이 목록은 요구사항이 아니라 **SPEC이 계속 개정되며 함께 바뀌는 대장**이다.

> 갱신하지 않는다.

## 1. 왜 전문 간 필드 연쇄를 아직 구현하지 않는가

국세 결제는 실제 업무 순서상 `501008`(국고 상세 고지내역 조회) → `800000`(카드 정보 조회) →
`902614`(국고 신용카드 승인요청)로 진행되고, 앞 전문의 응답값이 뒤 전문의 요청 필드로 들어간다.
그런데 SPEC을 전수 확인한 결과 **연쇄 근거의 수준이 구간마다 크게 달랐다**(2026-09-18 조사):

- `501008` → `902614`: **명문 규정 있음.** 단 그 안에도 절삭·표현 변환·출처 미지정이 섞여 있다(§2).
- `800000` → `902614`: **명문 규정 전무.** SPEC은 해당 필드를 인터넷지로 API 재조회로 채우라고만
  한다(§3).
- 세 전문의 **호출 순서를 규정한 문장 자체가 문서에 없다**(목차 절 순서가 유일한 암시).

Phase 29 착수 당시(2026-09-18)에는 연쇄 매핑의 근거 수준이 낮아 **추정을 정본으로 굳히지 않으려고**
연쇄를 범위 밖으로 뺐다. 그래서 Phase 29의 결제 화면(`PRD.md` §12)은 **모든 필드를 표현/길이에 맞는
임의값으로 채워 보내는 방식**으로 먼저 만들었고(연쇄 없음), Phase 29의 검증 대상도 연쇄 규칙이 아니라
**프레이밍(`#0` 길이)·POSITION 정합성·CP949 왕복·원캡이 채우는 카드리딩 필드**로 좁혀졌다. 이제
(2026-09-22) 값 출처가 전부 확정돼 연쇄는 **Phase 30**으로 착수한다 — 이 문서는 그 구현 근거를
SPEC 명문/사용자 확정으로 구분해 기록해 둔다.

### 근거 등급 표기

| 등급 | 뜻 |
|---|---|
| (가) | SPEC 원문에 "SET하라"는 **명시적 지시**가 있음 |
| (나) | 지시문은 없으나 **이름이 완전히 동일**해 사실상 자명 |
| (다) | **의미만 겹침** — 우리 추정 |
| (라) | 매칭 후보 없음 |

## 3. 조사 기록 — `800000` 응답 → `902614` 요청

**등급 (가)는 하나도 없다.** `902614` 설명절(p.16~17)·흐름도(p.14)·개요(1장, p.4) 어디에도
"800000" 또는 "카드 정보 조회"라는 표현이 **한 번도 등장하지 않는다.** SPEC은 해당 필드를
**인터넷지로 API 3종 재조회**로 채우라고만 지시한다:

- `#28` 수수료 — p.16 `API「카드 수수료 금액 조회(/igiro/v1/services/card-fee)」이용, 인터넷지로
  수납센터에서 재검증함`
- `#33` 카드사코드 — p.17 `API「납부가능 신용카드(간편결제)사 조회(/igiro/v1/services/avail-card)」통해
  서비스 가능한 카드사 선 조회 후 "card_code"(2자리) SET`
- `#34` 할부개월수 — p.17 `API「신용카드 할부 가능 개월 조회(/igiro/v1/services/card-installment)」통해
  해당 카드사의 가능한 할부 개월 수 선 확인 후 SET`

이름·의미가 겹치는 후보는 `902614` kiosk 구간 29개 필드 중 **4개뿐**이다:

| `902614` 요청 | 표현·길이 | `800000` 응답 | 표현·길이 | 문제 | 등급 |
|---|---|---|---|---|---|
| `#33` 카드사 코드 | **N**2 | `#17` 카드사 코드 | **AN**2 | 표현 AN→N | **(나) → Q1** |
| `#34` 할부 개월 수 | N2 | `#22` 카드 할부개월 LIST | AN60 (최대 30개) | 리스트→단일값, **선택 규칙 SPEC 없음** | **(다) → Q2** |
| `#28` 수수료 | N**15** | `#24` 납부대행 수수료 금액 | N**12** | 길이 12→15 | **(다) → Q3** |
| `#29` 총 납부 금액 | N**15** | `#25` 합계금액 | N**12** | 길이 12→15, 명칭 상이 | **(다) → Q3** |

`800000` 응답의 나머지 필드(`#18` 카드사명, `#19` 체크카드 여부, `#20` 납부가능 시간 여부,
`#21` 포인트 납부 가능 여부, `#23` 포인트 할부개월 LIST, `#26` 납부대행 수수료율,
`#27` API 세부 응답코드)는 `902614`에 대응 필드가 **없다**(라) — `800000` 자체에서 소비되는
(화면 표시/오류 진단) 값으로 보인다.
