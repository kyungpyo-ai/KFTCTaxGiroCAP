# PRD: KFTCTaxGiroCAP 결제 중계 기능

> 2차 개발 요구사항 정의서. 1차 범위(홈 화면 + 리더기 설정 화면 UX/UI, `docs/home_reader_setup/PRD_WPF.md`)는
> 완료됐고, 이 문서부터는 **실제 하드웨어(카드 리더기)와 VAN 서버 연동을 포함한 결제 중계 기능**을 다룬다.
> Phase 진행은 이 문서의 요구사항을 기준으로 `docs/home_reader_setup/ROADMAP.md`에 **Phase 7부터 이어서**
> 정의한다(새 ROADMAP 파일을 따로 만들지 않는다 — CLAUDE.md 정책).
>
> **통합 대상**: 이 기능은 별도 실행 파일이 아니라, 지금 작업 중인 `KFTCOneCAP.Wpf`(홈 화면·리더기 설정
> 화면 WPF 앱) 안에 백그라운드 서비스 형태로 통합한다(2026-08-18, 사용자 확정).

## 0. 문서 출처와 확정 범위

이 PRD는 사용자가 제공한 요구사항 원문을 그대로 옮기되, 프로젝트 문서 형식에 맞춰 재정리한 것이다. **§10
"미확정 사항"에 명시된 항목 외에는 이 문서가 곧 요구사항 원문**이며, 별도의 상세 SPEC 문서가 존재하지
않는다(특히 KFTC_GIRO.dll — 아래 §2.3 참고). 애매한 부분을 발견하면 추측하지 말고 사용자에게 확인한다.

## 1. 프로그램 개요

KFTCTaxGiroCAP은 POS 프로그램과 VAN 서버 사이에서 결제를 중계하는 Windows 프로그램이다.

- 프로그램 실행 시 `localhost:8002` 포트에 소켓 서버를 구동한다.
- POS 프로그램으로부터 결제 요청 전문을 수신한다.
- 결제 요청 수신 후 Reader DLL을 이용하여 카드 리더기를 제어하고 카드 리딩을 수행한다.
- 카드 리딩 결과를 이용하여 `KFTC_GIRO.dll`의 Export 함수 `FNAISCRDVAN`을 호출해 VAN 서버에 결제를 요청한다.
- VAN 서버의 응답을 POS 프로그램에 소켓으로 반환한다.

기본 흐름:

```text
POS 프로그램
   ↓ Socket (localhost:8002)
KFTCTaxGiroCAP (KFTCOneCAP.Wpf, 백그라운드 서비스)
   ↓ Reader DLL (ReaderSerial.dll)
카드 리더기
   ↓
KFTCTaxGiroCAP
   ↓ KFTC_GIRO.dll (FNAISCRDVAN)
VAN 서버
   ↓
KFTCTaxGiroCAP
   ↓ Socket
POS 프로그램
```

## 2. 기본 설정 및 연동 모듈

### 2.1 POS 식별번호

- POS 식별번호: `KFTCTAXGIROCAP01`
- **코드에 하드코딩한다**(2026-08-19 사용자 확정) — 레지스트리/설정 파일/UI 항목으로 두지 않는다. 무결성
  체크 이력 저장 시 이 값을 그대로 기록한다(§7).

### 2.2 리더기 연동

- 카드 리더기 제어는 `ReaderSerial.dll`을 사용한다. **연동 참조 자료는 이미 이 저장소에 준비되어 있다** —
  `docs/reader_dll/00_OVERVIEW.md`(인덱스), `docs/reader_dll/DLL연동가이드.md`(API 5종·CALLBACK 계약),
  `vendor/ReaderSerial/`(DLL/헤더/lib + 검증된 C# P/Invoke 샘플). SPEC 확인은
  `reader-pinpad-spec-expert`, 실제 P/Invoke 구현은 `reader-dll-integration-developer` 서브에이전트에
  위임한다.
- 이 기능이 실제로 쓰는 주요 전문은 다음과 같다(전부 `Reader_SendCommand`의 `commandCode`, SPEC 업무
  응답 코드는 `data`의 첫 2byte — `docs/reader_dll/DLL연동가이드.md` §3 참고).

  | 요청 | 응답 | 용도 |
  |---|---|---|
  | `0x60` | `0x70` | 초기화 |
  | `0x61` | `0x71` | 상태체크 |
  | `0x62` | `0x72` | 무결성 체크 |
  | `0x2B` | `0x3B` | 카드 리딩 |

- Reader DLL은 `READER_CALLBACK`으로 비동기 응답을 전달하므로, **중복 CALLBACK 및 동시 이벤트 처리에
  주의**해야 한다 — 상세 동시성 요구사항은 §8을 참고. CALLBACK 데이터 수명 규칙(콜백 실행 중에만 유효,
  즉시 복사 필요)은 `docs/reader_dll/DLL연동가이드.md` §2를 반드시 따른다.

#### 2.2.1 사용할 COM 포트와 통신 속도

- **COM 포트는 리더기 설정 화면에서 저장한 레지스트리 값을 읽어 사용한다** — `HKCU\Software\KFTC_VAN\
  KFTCTaxGiroCAP\SERIALPORT\COMPORT1_FIELD` / `COMPORT2_FIELD` (매핑 상세: `docs/home_reader_setup/PRD_WPF.md`
  §5). 값은 콤보 표시 문자열 그대로(`"COM 01"`, `"미사용"` 등)이므로 포트 번호로 변환해 `Reader_OpenPort`의
  `portNumber`(정수)에 넘긴다.
- **baudRate는 `115200` 고정**이다(2026-08-18 사용자 확정). 레지스트리/설정 항목으로 두지 않는다.

#### 2.2.2 포트 생명주기

- 포트는 **항상 열어둔다.** 앱 기동 시 설정된 포트를 열고, 그대로 유지한다.
  - 1차 범위 PRD의 "포트 열기" 토글(`PRD_WPF.md` §4.8, `PORT_ALWAYSOPEN`)은 **UI에서 제거된 상태**이며
    (자리만 `Visibility="Hidden"`으로 남아 있음), 이 기능은 되살리지 않는다 — 항상 열어두는 동작으로 확정.
- 기동 시 열기에 실패해도(리더기 미연결 등) 앱은 정상 기동하며, **결제 요청 시 다시 시도**한다(§2.2.4의
  재시도 래퍼가 담당).
- **포트를 닫는 경우는 하나뿐이다**: 리더기 설정 화면에서 사용자가 COM 포트 콤보를 변경할 때. 변경된 포트로
  다시 연다.

#### 2.2.3 리더기 이중화 (2대 동시 사용)

**하나의 결제 요청에 대해 설정된 리더기 2대 모두에 동시에 카드 리딩 명령을 보낸다.** 고객이 어느 리더기에
카드를 댈지 알 수 없으므로 양쪽 다 대기시키는 구성이다(병렬 거래가 아니다 — 거래는 여전히 §3.2/§8.1대로
한 번에 하나).

- 양쪽에 **동일한 명령**(`0x2B`, 같은 필드)을 보낸다.
- **먼저 최종 응답한 리더기의 결과를 채택**하고, 아직 대기 중인 나머지 리더기에는 **`0x60`(초기화)을 보내
  무효화**한다. `0x60`은 `WAITING_RESPONSE` 상태에서도 허용되며 대기 중이던 명령을 무엇이든 무효화하도록
  DLL이 설계돼 있어(`docs/reader_dll/DLL연동가이드.md` §1.4), 상대가 무슨 명령을 기다리든 성립한다.
- 이 "먼저 응답한 쪽 채택 + 나머지 무효화" 정책은 **DLL이 아니라 이 앱(POS)의 책임**이다 — DLL에는
  `SendCommandToAll` 류 API가 의도적으로 없다.
- **참조 구현**: `vendor/ReaderSerial/MfcSample/ReaderSerialTestUIDlg.cpp`의 `BroadcastFailover()`
  (원본 KFTCReaderDLL 프로젝트의 "페일오버 전송" 기능, 동일/상이 명령 양쪽 모두 실장비 검증 완료). 새로
  설계하지 말고 이 구현을 따른다.
- **한쪽만 사용 가능한 경우**(다른 쪽이 `"미사용"` 설정이거나 포트 열기 실패) — 가능한 쪽으로 그대로
  진행한다(N=1인 축약 사례로 자연스럽게 동작해야 하며, 별도 분기로 만들지 않는다).
- **양쪽 모두 `"미사용"`인 경우** — 포트 자체가 없으므로 카드 리딩을 시도하지 않고 즉시 오류 전문을
  POS에 반환한다(포트 열기 실패와는 구분되는 상황 — 그쪽은 §2.2.4의 재시도 대상이다).

#### 2.2.4 포트 오류 재시도 (필수 구현)

`Reader_SendCommand`를 직접 호출하지 않고 **반드시 재시도 래퍼를 경유**한다. 동작은
`vendor/ReaderSerial/CSharpSample/MainForm.cs`의 `SendCommandSafe()`를 그대로 따른다.

| 상황 | 처리 |
|---|---|
| `readerId` 없음 | 먼저 `Reader_OpenPort`로 확보 후 전송 |
| `READER_ERR_PORT_NOT_OPEN` | `Reader_ClosePort` → `Reader_OpenPort` → **1회만** 재전송. 재오픈 성공 시 **새 `readerId`로 반드시 덮어쓴다**(옛 id 재사용 금지) |
| `READER_ERR_SEND_FAIL` | 프레임 재동기화용 `0x60`을 방어적으로 전송(결과를 기다리지 않음), 원래 오류는 그대로 호출자에게 반환 |
| `READER_ERR_BUSY` | **복구 대상 아님** — 이미 다른 명령이 정상 진행 중이라는 뜻이므로 여기서 Close하면 그 명령을 죽인다. 그대로 반환 |

`Reader_IsPortOpen()`을 송신 전 사전 게이트로 쓰지 않는다 — `Reader_SendCommand`가 포트 상태를 원자적으로
검증하므로 중복이고, 체크와 송신 사이에 경합만 생긴다. UI 상태 표시 용도로만 쓴다.

### 2.3 VAN 서버 연동

- VAN 서버 통신은 `KFTC_GIRO.dll`을 사용한다. **이 DLL은 별도 SPEC 문서·샘플 소스가 없다** — 아래 함수
  시그니처와 사용 규칙이 현재 확보된 유일한 계약 정보다. DLL 파일 자체는
  `vendor/KftcGiro/KFTC_GIRO.dll`에 있다(32bit/x86, Phase 8에서 `docs/payment_relay/dll/`에서 이동 —
  `vendor/`는 외부 바이너리, `docs/`는 문서라는 기존 구분을 `vendor/ReaderSerial/`과 통일). 결제 알림창
  이미지 자산(§5.2)도 확보되는 대로 같은 `docs/payment_relay/`(예: `docs/payment_relay/images/`) 아래에 모은다.
- `KFTC_GIRO.dll`은 32bit(x86) DLL이므로 KFTCTaxGiroCAP(=`KFTCOneCAP.Wpf`)도 이 DLL을 직접 연동할 수
  있도록 **Win32(x86) 환경을 기준으로 구성**해야 한다 — `ReaderSerial.dll`과 동일한 제약(x86 전용,
  `PlatformTarget`을 `x86`으로 명시해야 함).
- 실제 Export 함수명은 `FNAISCRDVAN`이다. 호출 규약은 `__stdcall`이며 문자열 인자는 ANSI `char*` 기반이다.

  ```cpp
  int __stdcall FNAISCRDVAN(
      char* in_szMode,
      char* inData,
      char* outData,
      char* out_szRetCode,
      int int_iTimeout
  );
  ```

  - `szMode`: `R`(운영 서버) / `IT`(내부망 테스트 서버) / `OT`(외부망 테스트 서버)
  - 사용 예: `FNAISCRDVAN("OT", input, data, ret_code, 60)`
  - `nRet == 0`: DLL 통신 성공(**실제 거래 승인 성공을 의미하지 않는다** — `outData`의 VAN 응답 전문을
    파싱해 최종 승인/거절을 판단해야 함)
  - `nRet == -1`: DLL 통신 실패
  - `out_szRetCode`에는 DLL 처리 결과코드가 반환되므로 DLL 호출 결과와 함께 확인한다.
- `KFTC_GIRO.dll`은 실행 환경의 `KFTC_GIROPOS.ini` 설정(`IP`/`PORT`/`LOGDIR`/`LOGGING` 등)을 참조한다.
  DLL 내부에서 운영 환경은 `REAL`, 테스트 환경은 `TEST` 설정을 참조하므로, 실제 운영/테스트 서버 설정은
  배포 환경의 INI 파일과 함께 관리해야 한다(이 INI 파일 자체는 아직 이 저장소에 없음 — §10 참고).
- `MFC42.DLL`/`MSVCRT.dll`/`WSOCK32.dll` 등에 의존하므로, 대상 PC에 필요한 런타임/의존 DLL이 정상 제공돼야
  한다.
- `inData`/`outData`의 실제 전문 길이 및 출력 버퍼 크기는 VAN 통신 SPEC 확정 후 최종 결정한다(§10 미확정
  사항 — 현재는 임시 테스트 전문으로 개발한다).

## 3. 소켓 서버 요구사항

### 3.1 서버 구동

- 프로그램(=`KFTCOneCAP.Wpf`) 실행 시 `localhost:8002` 포트에 소켓 서버를 구동한다.
- POS 프로그램은 이 소켓 서버로 결제 요청 전문을 전송한다.

### 3.2 요청 처리 방식

- 결제 요청은 한 번에 하나만 처리한다.
- 현재 거래 처리 중 추가 소켓 요청이 들어오면 Queue에 저장한다.
- 현재 거래 종료 후 Queue에 저장된 요청을 수신 순서대로 처리한다.
- 동시에 두 개 이상의 거래가 리더기 또는 VAN 통신을 수행해서는 안 된다.

## 4. 결제 기능 요구사항

### 4.1 결제 요청 수신 — 처리 순서

POS로부터 결제 요청 전문을 수신하면 다음 순서로 결제를 처리한다.

1. 설정된 리더기 각각(최대 2대, §2.2.3)에 대해 **포트별로** 금일 무결성 체크 성공 이력을 확인한다.
2. 금일 성공 이력이 없는 리더기는 무결성 체크를 수행한다.
3. IC 카드 입력 안내창을 표시한다.
4. **무결성 체크에 성공한 리더기 전부에** `0x2B` 카드 리딩 전문을 동시에 요청한다(§2.2.3 이중화).
5. **먼저 최종 응답한** 리더기의 `0x3B` 결과를 채택하고, 나머지는 `0x60`으로 무효화한 뒤 후속 처리를 수행한다.
6. 정상 카드 리딩 시 `KFTC_GIRO.dll`의 `FNAISCRDVAN` 함수를 호출하여 VAN 서버에 결제를 요청한다.
7. VAN 응답 결과를 POS에 소켓으로 반환한다.

### 4.2 결제 전 무결성 체크

- 결제 요청 시 **설정된 리더기 각각의 COM Port를 기준으로** 금일 무결성 체크 성공 이력을 확인한다.
- 성공 이력이 있는 포트는 무결성 체크 없이 카드 리딩 단계로 진행한다.
- 성공 이력이 없으면 다음 순서로 수행한다: `0x61` 요청 → `0x71` 응답 → 리더기 인증 식별번호/모듈ID
  파싱 → `0x62` 요청 → `0x72` 응답.
- `0x72` 응답코드가 `00`이면 성공으로 처리한다.
- **리더기 2대를 쓰는 경우 양쪽 모두 무결성 체크를 수행하고, 성공한 리더기만 카드 리딩에 참여시킨다**
  (2026-08-18 확정). 한쪽이 실패해도 나머지 한쪽이 성공했다면 그 리더기로 거래를 진행한다 — 양쪽 모두
  실패했을 때만 거래를 오류로 끝낸다.
- 수행 결과는 포트별로 로컬 DB에 저장한다(§7).

### 4.3 정상 IC 결제

- IC 카드 요청 시 `BG_IMG_IC.bmp` 기반 알림창을 표시한다.
- **참여 리더기 전체에** `0x2B` 전문을 동시에 요청한다(§2.2.3). 거래구분은 `ARQo`로 설정하며, **두 리더기에
  동일한 명령·동일한 필드**를 보낸다. 나머지 요청 필드는 리더기 샘플 소스를 참고한다
  (`vendor/ReaderSerial/CSharpSample/`).
- 먼저 `0x3B` 전문으로 최종 응답한 리더기의 결과를 채택하고, 나머지 리더기는 `0x60`으로 무효화한다.
- 채택한 응답의 응답코드가 `00`이면 정상 카드 리딩으로 처리한다.
- `0x3B` 응답 데이터를 파싱해 VAN 요청 데이터를 생성하고, `FNAISCRDVAN`을 호출해 VAN 서버에 결제를
  요청한다.

> **이하 §4.4~§4.6의 후속 처리는 모두 "채택된 리더기" 기준이다.** 응답을 채택한 시점에 나머지 리더기는 이미
> 무효화됐으므로, 재요청·초기화 등은 그 리더기 하나만 대상으로 한다(2026-08-18 확정).

### 4.4 FALLBACK 처리

- IC 리딩 결과 `0x3B` 응답코드가 `07`이면 FALLBACK 거래로 처리한다.
- 알림창을 `BG_IMG_MS` 기반 화면으로 변경한다.
- **응답한 그 리더기에만** `0x2B` 전문을 다시 요청한다(양쪽에 다시 뿌리지 않는다 — 고객이 이미 그 리더기
  앞에 있기 때문). 거래구분은 `F`로 설정한다.

### 4.5 응답코드 12 처리

- `0x3B` 응답코드가 `12`이면 **응답한 그 리더기에만** `0x2B` 전문을 다시 요청한다. 거래구분은 기존과
  동일하게 `ARQo`.

### 4.6 기타 Reader 응답코드 처리

- `0x3B` 응답코드가 `00`/`07`/`12` 이외면 카드 리딩 실패로 처리한다.
- Reader 초기화(`0x60`)를 요청한다.
- POS에 Reader 오류 및 실패 원인을 응답한다.

### 4.7 Reader DLL 연동 실패

- Reader DLL 호출 또는 CALLBACK 처리 자체가 실패한 경우 "DLL 연동 오류"로 처리한다.
- POS에 DLL 연동 오류 및 실패 원인을 응답한다.
- **Reader 응답코드에 의한 실패**(§4.6)와 **DLL 자체 연동 실패**(이 항목)는 구분해서 처리한다.

### 4.8 사용자 취소

- 결제 알림창의 취소 버튼 클릭 시 거래를 취소한다.
- **아직 응답 대기 중인 모든 리더기에** 초기화(`0x60`) 요청을 수행한다(이중화로 2대가 대기 중일 수 있으므로
  한쪽만 정리하면 나머지가 카드를 계속 기다린다).
- POS에 사용자 취소 결과를 응답한다.
- 카드 리딩 CALLBACK과 취소가 동시에 발생할 경우 둘 중 하나의 이벤트만 유효하게 처리되어야 한다(§8).

### 4.9 결제 Timeout

- 카드 입력 대기 시간은 최대 **120초**.
- 120초 동안 카드를 입력하지 않으면 자체 Timeout 처리한다.
- Timeout 발생 시 **응답 대기 중인 모든 리더기에** 초기화(`0x60`)를 수행한다(§4.8과 동일한 이유).
- POS에 Timeout 결과를 응답한다.
- Timeout과 Reader CALLBACK이 동시에 발생하더라도 한 개의 결과만 처리되어야 한다(§8).

### 4.10 VAN 서버 통신

- 정상 카드 리딩 후 VAN 통신 시작 시 `BG_IMG_PROCESSING` 기반 화면으로 변경한다.
- `FNAISCRDVAN` 호출 시 Mode를 전달한다 — **현재는 `OT`(외부망 테스트) 고정**이며, 운영 환경별 선택
  (`R`/`IT`/`OT`)은 추후 별도 옵션으로 다룬다(2026-08-18 사용자 확정, §11).
- `nRet == 0`이면 DLL 통신 성공으로 판단하고, `outData`의 VAN 응답 전문을 파싱해 최종 거래 결과를
  판단해 POS에 전달한다.
- `nRet == -1`이면 VAN DLL 통신 실패로 처리한다. `out_szRetCode`도 함께 확인해 오류 원인을 판단한다.
- DLL 호출은 성공했지만 VAN 응답 전문의 거래 결과가 실패/거절이면 "VAN 서버 거절"로 처리한다.
- **"VAN DLL 통신 실패"와 "VAN 서버 거절"은 서로 구분**해서 처리한다.
- 실패 시 Reader 초기화를 수행하고 POS에 오류 및 원인을 응답한다.

## 5. 결제 알림창 요구사항

### 5.1 표시 정책

- 결제 중 사용자에게 보여주는 화면은 결제 알림창만 사용한다.
- 결제 요청 때문에 `KFTCOneCAP.Wpf` 메인 화면(홈 화면)이 전면에 노출되어서는 안 된다.
- 메인 화면이 사용자 조작으로 전면에 올라와 있었더라도 결제 완료 후에는 다시 백그라운드 상태로
  이동해야 한다.
- 결제 알림창은 항상 다른 프로그램보다 상단에 표시한다(`Topmost` 등).

### 5.2 화면 종류

이미지 자산은 `docs/payment_relay/images/`에 확보되어 있다(2026-08-18). 각 화면마다 **기본 크기(750×650)**
와 **`_VERYSMALL` 접미사가 붙은 축소 크기(375×325, 정확히 1/2 배율)** 두 벌이 제공된다 — 추후 알림창
크기 조절 기능(사용자 확정, 아직 상세 요구사항 미정) 대비용으로 보인다. 지금 단계에서는 두 크기 모두
그대로 보관하고, 실제 "크기 조절" 요구사항이 확정되면 그때 배율/전환 트리거를 정의한다.

실제 UI 디자인은 이 이미지 파일 기준으로 구현한다.

### 5.3 ESC 키 처리

- 결제 알림창이 표시되어 있는 동안에만 ESC 키를 Hooking한다.
- ESC 키 입력은 알림창의 취소 버튼 클릭과 동일하게 처리한다.
- 알림창이 닫히면 ESC 키 Hooking을 해제한다.

### 6.1 초기화

- Reader `0x60` 요청 → `0x70` 응답. 응답코드 `00`이면 성공.

### 6.2 상태체크

- 성공: `리더기 상태체크 성공\n리더기 인증 식별번호 : XXXXX\n모듈 ID : XXXXX`
- 실패: `리더기 상태체크 실패\n{실패 원인}`

### 6.3 키다운로드

- 기능 버튼만 제공한다. 실제 동작은 추후 구현(§11).

### 6.4 무결성체크

1. Reader `0x61` 요청
2. `0x71` 응답 수신
3. 리더기 인증 식별번호/모듈 ID 파싱
4. Reader `0x62` 요청
5. `0x72` 응답 수신
6. `0x72` 응답코드가 `00`이면 성공

- 성공: `리더기 무결성 체크 성공\n리더기 인증 식별번호 : XXXXX\n모듈 ID : XXXXX`
- 실패: `리더기 무결성 체크 실패\n{실패 원인}`

### 6.5 업데이트

- 기능 버튼만 제공한다. 실제 동작은 추후 구현(§11).

### 6.6 리더기 오류 표시 공통사항

- 전문 응답코드에 의한 실패와 Reader DLL 연동 실패를 구분해서 표시한다.
- 가능하면 실패 원인을 사용자에게 함께 출력한다.

## 7. 무결성 체크 정보 저장 요구사항

- 무결성 체크 이력은 SQLite 등 클라이언트용 로컬 DB에 저장한다.
- 저장 항목: 체크 일시, COM Port, 결과, 응답코드, 모듈 ID, 리더기 인증 식별번호, POS 식별번호.
- 결제 시 "금일 동일 COM Port의 무결성 체크 성공 이력" 조회가 가능해야 한다(§4.2).
- 리더기 설정 화면의 "무결성 체크 정보" 리스트(`docs/home_reader_setup/PRD_WPF.md` 4.6, 1차 범위에서는
  정적 빈 상태만 구현됨)도 이 DB를 조회해 실제 데이터를 표시하도록 연동한다.

## 8. 거래 처리 및 동기화 요구사항

### 8.1 중복 거래 방지

- 하나의 거래가 완료되기 전 다른 거래가 동시에 실행되어서는 안 된다. 추가 요청은 Queue에서 대기한다.

### 8.2 중복 카드 리딩 방지

- 하나의 거래에서 카드 리딩 결과가 두 번 이상 처리되어서는 안 된다.
- Reader DLL CALLBACK이 중복 호출되더라도 최초 유효 응답만 처리해야 한다.

### 8.3 동시 이벤트 처리

다음이 동시에 발생하더라도 하나의 이벤트만 최종 처리되어야 한다.

- 카드 리딩 완료 + 사용자 취소
- 카드 리딩 완료 + Timeout
- 사용자 취소 + Timeout
- Reader CALLBACK 중복 수신

### 8.4 거래 종료 후 데이터 정리

- 거래 종료 시 그 거래에서 사용한 카드 리딩 데이터를 모두 삭제한다.
- 이전 거래의 Reader CALLBACK/카드 데이터가 다음 거래에 영향을 주어서는 안 된다.

## 9. 안정성 및 성능 요구사항

- `KFTC_GIRO.dll`이 32bit(x86)이므로 빌드 환경(`PlatformTarget`)을 이 DLL이 로드 가능한 아키텍처로
  맞춰야 한다(`ReaderSerial.dll`과 동일 제약, §2.2/§2.3).
- `KFTC_GIRO.dll` 호출 시 ANSI 문자열 변환과 입출력 Buffer 크기를 정확히 관리해 메모리 침범이 발생하지
  않도록 한다.
- 대상 PC에서 `KFTC_GIRO.dll`의 의존 DLL/런타임이 정상 로드되지 않는 경우에도 프로그램이 비정상 종료되지
  않고 오류로 처리되어야 한다.
- Reader DLL 오류, VAN 통신 오류, Socket 통신 오류로 프로그램 전체가 종료되어서는 안 된다.
- 결제 처리 중 발생 가능한 예외를 충분히 처리해야 한다.
- 장시간 실행 시 메모리 누수가 발생하지 않도록 관리한다.
- 거래 종료 시 CALLBACK, Timer, Hook 등 거래 관련 리소스를 정상적으로 정리한다.
- 카드 리딩 데이터는 거래 종료 후 즉시 삭제한다.
- 결제 처리 속도는 최대한 빠르게 유지하되, **처리 속도보다 중복 거래/중복 카드 리딩 방지가 우선**한다.

## 10. 현재 미확정 사항 및 개발 시 고려사항

다음 통신 전문/자료는 아직 확정되지 않았다.

- POS ↔ KFTCTaxGiroCAP 소켓 요청/응답 전문
- KFTCTaxGiroCAP ↔ VAN 요청/응답 전문
- `KFTC_GIRO.dll`에 전달할 VAN 입력 전문의 정확한 길이/구성, `outData` 출력 전문 길이/필요 Buffer 크기
- `KFTC_GIRO.dll`용 `KFTC_GIROPOS.ini` 설정 파일(아직 이 저장소에 없음 — 배포 환경에서 별도 확보 필요)
- 알림창 "크기 조절" 기능의 상세 요구사항(트리거 조건, 기본/축소 중 무엇을 기본값으로 할지 등) — 이미지
  자산(§5.2)만 먼저 확보된 상태이며 동작 요구사항은 아직 사용자로부터 정의되지 않음
> **멀티패드 설정(`MULTIPAD1_FIELD`/`MULTIPAD2_FIELD`)은 이번 범위에서 사용하지 않는다**(2026-08-19 확정).
> 1차 PRD의 안내 문구(`PRD_WPF.md` §4.10)는 "ON: QR 기능 사용 가능"이라 QR/스캐너 기능을 가리키는데,
> `ReaderSerial.dll`이 말하는 "멀티패드"는 리더기와 핀패드가 한 COM 포트를 공유하는 하드웨어 구성을 뜻한다
> (`docs/reader_dll/DLL연동가이드.md` §6.1) — **같은 단어가 서로 다른 개념을 가리킨다.** 현재 PRD에 핀패드·QR
> 요구사항이 없으므로 이 값을 읽어 쓰지 않으며, `Reader_OpenPort`의 `pinpadCallback`에는 `nullptr`을 넘긴다
> (리더기 전용 연동). 향후 QR/핀패드 요구사항이 생기면 그때 두 개념 중 어느 쪽인지부터 확정한다.

### 10.1 확정된 사항 (2026-08-18 사용자 확인)

로드맵 작성 중 발견돼 이번에 확정된 항목들 — 상세는 각 절 참고.

| 항목 | 결정 | 근거 절 |
|---|---|---|
| 결제에 쓸 COM 포트 | 리더기 설정 화면이 레지스트리에 저장한 값을 읽어 사용 | §2.2.1 |
| baudRate | `115200` 고정 | §2.2.1 |
| 포트 생명주기 | 항상 열어둠(기동 시 열기, 실패 시 결제 때 재시도). 콤보로 포트 변경할 때만 닫음 | §2.2.2 |
| 리더기 2대 사용 방식 | 이중화 — 한 거래에서 양쪽에 동시 명령, 먼저 응답한 쪽 채택 + 나머지 `0x60` 무효화 | §2.2.3 |
| 한쪽만 사용 가능할 때 | 가능한 쪽으로 그대로 진행 | §2.2.3 |
| 양쪽 모두 "미사용"일 때 | 즉시 오류 전문 반환(포트 열기 실패와 구분) | §2.2.3 |
| 포트 오류 재시도 | `SendCommandSafe` 패턴 필수 구현 | §2.2.4 |
| 무결성 체크 × 2대 | 둘 다 체크, 성공한 쪽만 카드 리딩 참여 | §4.2 |
| FALLBACK/`12` 재요청 대상 | 응답을 채택한 그 리더기에만 | §4.4, §4.5 |
| 카드 리딩 명령 | 양쪽 모두 `0x2B` 동일 | §4.3 |
| VAN Mode | `OT` 고정(추후 옵션화) | §4.10 |
| AOP 제약/TRANSINFO_AOP | 이번 범위에서도 제외 | §6 |
| POS 식별번호 | `KFTCTAXGIROCAP01` 코드에 하드코딩(설정 항목 아님) | §2.1 |
| 멀티패드 설정 | 이번 범위에서 사용하지 않음(`pinpadCallback`은 `nullptr`) | §10 |

따라서 현재 개발 단계에서는 **임시 테스트 전문**을 정의해 다음 기능 위주로 로직을 검증한다: 소켓 요청
수신/Queue 처리, Reader 제어, 무결성 체크, 카드 리딩, FALLBACK, 사용자 취소, Timeout, VAN DLL 호출(실제
`FNAISCRDVAN` 호출은 하되 입출력 전문은 임시), 전체 결제 Flow. 실제 통신 SPEC이 확정되면 전문 생성/파싱
부분만 교체하면 되도록 구현해, 전문 변경이 Reader 제어·결제 Flow 전체 로직에 번지지 않게 한다(계층 분리
원칙 — Phase 설계 시 이 경계를 명시적으로 둔다).
