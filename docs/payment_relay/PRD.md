# PRD: KFTCTaxGiroCAP 결제 중계 기능

> 2차 개발 요구사항 정의서. 1차 범위(홈 화면 + 리더기 설정 화면 UX/UI, `docs/home_reader_setup/PRD_WPF.md`)는
> 완료됐고, 이 문서부터는 **실제 하드웨어(카드 리더기)와 VAN 서버 연동을 포함한 결제 중계 기능**을 다룬다.
> Phase 진행은 이 문서의 요구사항을 기준으로 `docs/home_reader_setup/ROADMAP.md`에 **Phase 7부터 이어서**
> 정의한다(새 ROADMAP 파일을 따로 만들지 않는다 — CLAUDE.md 정책).
>
> **통합 대상**: 이 기능은 별도 실행 파일이 아니라, 지금 작업 중인 `KFTCOneCAP.Wpf`(홈 화면·리더기 설정
> 화면 WPF 앱) 안에 백그라운드 서비스 형태로 통합한다(2026-08-18, 사용자 확정).

## 0. 문서 출처와 확정 범위

이 PRD는 사용자가 제공한 요구사항 원문을 그대로 옮기되, 프로젝트 문서 형식에 맞춰 재정리한 것이다. **§10
"미확정 사항"에 명시된 항목 외에는 이 문서가 곧 요구사항 원문**이며, 별도의 상세 SPEC 문서가 존재하지
않는다(특히 KFTC_GIRO.dll — 아래 §2.3 참고). 애매한 부분을 발견하면 추측하지 말고 사용자에게 확인한다.

## 1. 프로그램 개요

KFTCTaxGiroCAP은 POS 프로그램과 VAN 서버 사이에서 결제를 중계하는 Windows 프로그램이다.

- 프로그램 실행 시 `localhost:8002` 포트에 소켓 서버를 구동한다.
- POS 프로그램으로부터 결제 요청 전문을 수신한다.
- 결제 요청 수신 후 Reader DLL을 이용하여 카드 리더기를 제어하고 카드 리딩을 수행한다.
- 카드 리딩 결과를 이용하여 `KFTC_GIRO.dll`의 Export 함수 `FNAISCRDVAN`을 호출해 VAN 서버에 결제를 요청한다.
- VAN 서버의 응답을 POS 프로그램에 소켓으로 반환한다.

기본 흐름:

```text
POS 프로그램
   ↓ Socket (localhost:8002)
KFTCTaxGiroCAP (KFTCOneCAP.Wpf, 백그라운드 서비스)
   ↓ Reader DLL (ReaderSerial.dll)
카드 리더기
   ↓
KFTCTaxGiroCAP
   ↓ KFTC_GIRO.dll (FNAISCRDVAN)
VAN 서버
   ↓
KFTCTaxGiroCAP
   ↓ Socket
POS 프로그램
```

## 2. 기본 설정 및 연동 모듈

### 2.1 POS 식별번호

- POS 식별번호: `KFTCTAXGIROCAP01`
- **코드에 하드코딩한다**(2026-08-19 사용자 확정) — 레지스트리/설정 파일/UI 항목으로 두지 않는다. 무결성
  체크 이력 저장 시 이 값을 그대로 기록한다(§7).

### 2.2 리더기 연동

- 카드 리더기 제어는 `ReaderSerial.dll`을 사용한다. **연동 참조 자료는 이미 이 저장소에 준비되어 있다** —
  `docs/reader_dll/00_OVERVIEW.md`(인덱스), `docs/reader_dll/DLL연동가이드.md`(API 5종·CALLBACK 계약),
  `vendor/ReaderSerial/`(DLL/헤더/lib + 검증된 C# P/Invoke 샘플). SPEC 확인은
  `reader-pinpad-spec-expert`, 실제 P/Invoke 구현은 `reader-dll-integration-developer` 서브에이전트에
  위임한다.
- 이 기능이 실제로 쓰는 주요 전문은 다음과 같다(전부 `Reader_SendCommand`의 `commandCode`, SPEC 업무
  응답 코드는 `data`의 첫 2byte — `docs/reader_dll/DLL연동가이드.md` §3 참고).

  | 요청 | 응답 | 용도 |
  |---|---|---|
  | `0x60` | `0x70` | 초기화 |
  | `0x61` | `0x71` | 상태체크 |
  | `0x62` | `0x72` | 무결성 체크 |
  | `0x2B` | `0x3B` | 카드 리딩 |

- Reader DLL은 `READER_CALLBACK`으로 비동기 응답을 전달하므로, **중복 CALLBACK 및 동시 이벤트 처리에
  주의**해야 한다 — 상세 동시성 요구사항은 §8을 참고. CALLBACK 데이터 수명 규칙(콜백 실행 중에만 유효,
  즉시 복사 필요)은 `docs/reader_dll/DLL연동가이드.md` §2를 반드시 따른다.

#### 2.2.1 사용할 COM 포트와 통신 속도

- **COM 포트는 리더기 설정 화면에서 저장한 레지스트리 값을 읽어 사용한다** — `HKCU\Software\KFTC_VAN\
  KFTCTaxGiroCAP\SERIALPORT\COMPORT1_FIELD` / `COMPORT2_FIELD` (매핑 상세: `docs/home_reader_setup/PRD_WPF.md`
  §5). 값은 콤보 표시 문자열 그대로(`"COM 01"`, `"미사용"` 등)이므로 포트 번호로 변환해 `Reader_OpenPort`의
  `portNumber`(정수)에 넘긴다.
- **baudRate는 `115200` 고정**이다(2026-08-18 사용자 확정). 레지스트리/설정 항목으로 두지 않는다.

#### 2.2.2 포트 생명주기

- 포트는 **항상 열어둔다.** 앱 기동 시 설정된 포트를 열고, 그대로 유지한다.
  - 1차 범위 PRD의 "포트 열기" 토글(`PRD_WPF.md` §4.8, `PORT_ALWAYSOPEN`)은 **UI에서 제거된 상태**이며
    (자리만 `Visibility="Hidden"`으로 남아 있음), 이 기능은 되살리지 않는다 — 항상 열어두는 동작으로 확정.
- 기동 시 열기에 실패해도(리더기 미연결 등) 앱은 정상 기동하며, **결제 요청 시 다시 시도**한다(§2.2.4의
  재시도 래퍼가 담당).
- **포트를 닫는 경우는 하나뿐이다**: 리더기 설정 화면에서 사용자가 COM 포트 콤보를 변경할 때. 변경된 포트로
  다시 연다.

#### 2.2.3 리더기 이중화 (2대 동시 사용)

**하나의 결제 요청에 대해 설정된 리더기 2대 모두에 동시에 카드 리딩 명령을 보낸다.** 고객이 어느 리더기에
카드를 댈지 알 수 없으므로 양쪽 다 대기시키는 구성이다(병렬 거래가 아니다 — 거래는 여전히 §3.2/§8.1대로
한 번에 하나).

- 양쪽에 **동일한 명령**(`0x2B`, 같은 필드)을 보낸다.
- **먼저 최종 응답한 리더기의 결과를 채택**하고, 아직 대기 중인 나머지 리더기에는 **`0x60`(초기화)을 보내
  무효화**한다. `0x60`은 `WAITING_RESPONSE` 상태에서도 허용되며 대기 중이던 명령을 무엇이든 무효화하도록
  DLL이 설계돼 있어(`docs/reader_dll/DLL연동가이드.md` §1.4), 상대가 무슨 명령을 기다리든 성립한다.
- 이 "먼저 응답한 쪽 채택 + 나머지 무효화" 정책은 **DLL이 아니라 이 앱(POS)의 책임**이다 — DLL에는
  `SendCommandToAll` 류 API가 의도적으로 없다.
- **참조 구현**: `vendor/ReaderSerial/MfcSample/ReaderSerialTestUIDlg.cpp`의 `BroadcastFailover()`
  (원본 KFTCReaderDLL 프로젝트의 "페일오버 전송" 기능, 동일/상이 명령 양쪽 모두 실장비 검증 완료). 새로
  설계하지 말고 이 구현을 따른다.
- **한쪽만 사용 가능한 경우**(다른 쪽이 `"미사용"` 설정이거나 포트 열기 실패) — 가능한 쪽으로 그대로
  진행한다(N=1인 축약 사례로 자연스럽게 동작해야 하며, 별도 분기로 만들지 않는다).
- **양쪽 모두 `"미사용"`인 경우** — 포트 자체가 없으므로 카드 리딩을 시도하지 않고 즉시 오류 전문을
  POS에 반환한다(포트 열기 실패와는 구분되는 상황 — 그쪽은 §2.2.4의 재시도 대상이다).

#### 2.2.4 포트 오류 재시도 (필수 구현)

`Reader_SendCommand`를 직접 호출하지 않고 **반드시 재시도 래퍼를 경유**한다. 동작은
`vendor/ReaderSerial/CSharpSample/MainForm.cs`의 `SendCommandSafe()`를 그대로 따른다.

| 상황 | 처리 |
|---|---|
| `readerId` 없음 | 먼저 `Reader_OpenPort`로 확보 후 전송 |
| `READER_ERR_PORT_NOT_OPEN` | `Reader_ClosePort` → `Reader_OpenPort` → **1회만** 재전송. 재오픈 성공 시 **새 `readerId`로 반드시 덮어쓴다**(옛 id 재사용 금지) |
| `READER_ERR_SEND_FAIL` | 프레임 재동기화용 `0x60`을 방어적으로 전송(결과를 기다리지 않음), 원래 오류는 그대로 호출자에게 반환 |
| `READER_ERR_BUSY` | **복구 대상 아님** — 이미 다른 명령이 정상 진행 중이라는 뜻이므로 여기서 Close하면 그 명령을 죽인다. 그대로 반환 |

`Reader_IsPortOpen()`을 송신 전 사전 게이트로 쓰지 않는다 — `Reader_SendCommand`가 포트 상태를 원자적으로
검증하므로 중복이고, 체크와 송신 사이에 경합만 생긴다. UI 상태 표시 용도로만 쓴다.

### 2.3 VAN 서버 연동

- VAN 서버 통신은 `KFTC_GIRO.dll`을 사용한다. **이 DLL은 별도 SPEC 문서·샘플 소스가 없다** — 아래 함수
  시그니처와 사용 규칙이 현재 확보된 유일한 계약 정보다. DLL 파일 자체는
  `vendor/KftcGiro/KFTC_GIRO.dll`에 있다(32bit/x86, Phase 8에서 `docs/payment_relay/dll/`에서 이동 —
  `vendor/`는 외부 바이너리, `docs/`는 문서라는 기존 구분을 `vendor/ReaderSerial/`과 통일). 결제 알림창
  이미지 자산(§5.2)도 확보되는 대로 같은 `docs/payment_relay/`(예: `docs/payment_relay/images/`) 아래에 모은다.
- `KFTC_GIRO.dll`은 32bit(x86) DLL이므로 KFTCTaxGiroCAP(=`KFTCOneCAP.Wpf`)도 이 DLL을 직접 연동할 수
  있도록 **Win32(x86) 환경을 기준으로 구성**해야 한다 — `ReaderSerial.dll`과 동일한 제약(x86 전용,
  `PlatformTarget`을 `x86`으로 명시해야 함).
- 실제 Export 함수명은 `FNAISCRDVAN`이다. 호출 규약은 `__stdcall`이며 문자열 인자는 ANSI `char*` 기반이다.

  ```cpp
  int __stdcall FNAISCRDVAN(
      char* in_szMode,
      char* inData,
      char* outData,
      char* out_szRetCode,
      int int_iTimeout
  );
  ```

  - `szMode`: `R`(운영 서버) / `IT`(내부망 테스트 서버) / `OT`(외부망 테스트 서버)
  - 사용 예: `FNAISCRDVAN("OT", input, data, ret_code, 60)`
  - `nRet == 0`: DLL 통신 성공(**실제 거래 승인 성공을 의미하지 않는다** — `outData`의 VAN 응답 전문을
    파싱해 최종 승인/거절을 판단해야 함)
  - `nRet == -1`: DLL 통신 실패
  - `out_szRetCode`에는 DLL 처리 결과코드가 반환되므로 DLL 호출 결과와 함께 확인한다.
- `KFTC_GIRO.dll`은 실행 환경의 `KFTC_GIROPOS.ini` 설정(`IP`/`PORT`/`LOGDIR`/`LOGGING` 등)을 참조한다.
  DLL 내부에서 운영 환경은 `REAL`, 테스트 환경은 `TEST` 설정을 참조하므로, 실제 운영/테스트 서버 설정은
  배포 환경의 INI 파일과 함께 관리해야 한다(이 INI 파일 자체는 아직 이 저장소에 없음 — §10 참고).
- `MFC42.DLL`/`MSVCRT.dll`/`WSOCK32.dll` 등에 의존하므로, 대상 PC에 필요한 런타임/의존 DLL이 정상 제공돼야
  한다.
- `inData`/`outData`의 실제 전문 길이 및 출력 버퍼 크기는 VAN 통신 SPEC 확정 후 최종 결정한다(§10 미확정
  사항 — 현재는 임시 테스트 전문으로 개발한다).

## 3. 소켓 서버 요구사항

### 3.1 서버 구동

- 프로그램(=`KFTCOneCAP.Wpf`) 실행 시 `localhost:8002` 포트에 소켓 서버를 구동한다.
- POS 프로그램은 이 소켓 서버로 결제 요청 전문을 전송한다.

### 3.2 요청 처리 방식

- 결제 요청은 한 번에 하나만 처리한다.
- 현재 거래 처리 중 추가 소켓 요청이 들어오면 Queue에 저장한다.
- 현재 거래 종료 후 Queue에 저장된 요청을 수신 순서대로 처리한다.
- 동시에 두 개 이상의 거래가 리더기 또는 VAN 통신을 수행해서는 안 된다.

### 3.3 전문 구조 (2026-08-26 확정, Phase 17 — SPEC 확보로 §10 미확정 해소)

`국세 베리어프리 키오스크용 전산설계서(POS-원캡)_20260831.pdf`가 정본이다(**2026-08-31 개정** — 800000
전문에 `#26 납부대행 수수료율` 필드 추가, §4.11 하단 참고. 20260826판은 저장소에 더는 없음). POS는 다음
**3종의 독립 전문**을 보낸다 — "요청 1건 = 결제 1건"이 아니라 각 전문이 서로 다른 독립 기능이다.

| 전문 | 거래구분 코드 | 본문 길이 | 카드리딩 | 원캡이 채우는 필드 |
|---|---|---|---|---|
| 국고 상세 고지내역 조회 | `501008` | 706 | 없음(순수 중계) | 없음 |
| 카드 정보 조회 | `800000` | 500 | 있음(BIN만 사용) | `#14` BIN(8자리) |
| 국고 신용카드 승인 요청 | `902614` | 1500 | 있음 | `#43,44,45,46,48,50,51,53` 8개(`#51`은 Phase 18) |

- **전문마다 TCP 연결을 새로 연다** — 3전문은 하나의 거래로 묶이지 않는다. `800000`에서 읽은 카드
  데이터를 `902614`로 넘기지 않으며, 사용자는 카드를 **최대 2회** 댄다.
- 전문 길이(`#0`, 4바이트)는 **본문 길이**를 담는다 — 소켓에 실제로 나가는 바이트는 `본문+4`(예:
  `902614`는 1504바이트).
- 원캡↔VAN 구간(§2.3)도 **같은 전문 형식**이다 — VAN이 실제로 응답하면(승인/거절 무관) 그 바이트를
  그대로 POS에 중계한다. 응답 해석(승인/거절 판정)은 OneCAP이 하지 않는다.

## 4. 결제 기능 요구사항

> **§4.1~§4.10은 `902614`(국고 신용카드 승인 요청) 전문 기준으로 서술한다** — 이 절이 원래 이 PRD의
> 주 대상이었고 카드리딩·VAN 승인이 전부 여기 걸린다(2026-08-26, §3.3 확정 사항 반영). `501008`은
> 카드리딩·VAN 승인 절차 없이 곧바로 §4.10 방식으로 VAN에 중계하고(§3.3), `800000`은 §4.2~§4.6의
> 카드리딩 절차를 `902614`와 동일하게 거치되 채워 넣는 값만 `#14` BIN 하나로 다르다(§3.3 표).

### 4.1 결제 요청 수신 — 처리 순서

POS로부터 결제 요청 전문을 수신하면 다음 순서로 결제를 처리한다.

1. 설정된 리더기 각각(최대 2대, §2.2.3)에 대해 **포트별로** 금일 무결성 체크 성공 이력을 확인한다.
2. 금일 성공 이력이 없는 리더기는 무결성 체크를 수행한다.
3. IC 카드 입력 안내창을 표시한다.
4. **무결성 체크에 성공한 리더기 전부에** `0x2B` 카드 리딩 전문을 동시에 요청한다(§2.2.3 이중화).
5. **먼저 최종 응답한** 리더기의 `0x3B` 결과를 채택하고, 나머지는 `0x60`으로 무효화한 뒤 후속 처리를 수행한다.
6. 정상 카드 리딩 시 원캡 담당 필드(§3.3 표)를 채운 요청 전문을 `KFTC_GIRO.dll`의 `FNAISCRDVAN` 함수로
   VAN 서버에 전달한다.
7. VAN 응답 전문을 그대로(해석 없이) POS에 중계한다 — VAN이 응답을 못 준 경우(DLL 통신 실패)에만
   원캡이 직접 실패 응답을 합성한다(§4.10).

### 4.2 결제 전 무결성 체크

- 결제 요청 시 **설정된 리더기 각각의 COM Port를 기준으로** 금일 무결성 체크 성공 이력을 확인한다.
- 성공 이력이 있는 포트는 무결성 체크 없이 카드 리딩 단계로 진행한다.
- 성공 이력이 없으면 다음 순서로 수행한다: `0x61` 요청 → `0x71` 응답 → 리더기 인증 식별번호/모듈ID
  파싱 → `0x62` 요청 → `0x72` 응답.
- `0x72` 응답코드가 `00`이면 성공으로 처리한다.
- **리더기 2대를 쓰는 경우 양쪽 모두 무결성 체크를 수행하고, 성공한 리더기만 카드 리딩에 참여시킨다**
  (2026-08-18 확정). 한쪽이 실패해도 나머지 한쪽이 성공했다면 그 리더기로 거래를 진행한다 — 양쪽 모두
  실패했을 때만 거래를 오류로 끝낸다.
- 수행 결과는 포트별로 로컬 DB에 저장한다(§7).

### 4.3 정상 IC 결제

- IC 카드 요청 시 `BG_IMG_IC.bmp` 기반 알림창을 표시한다.
- **참여 리더기 전체에** `0x2B` 전문을 동시에 요청한다(§2.2.3). 거래구분은 `ARQo`로 설정하며, **두 리더기에
  동일한 명령·동일한 필드**를 보낸다. 나머지 요청 필드는 리더기 샘플 소스를 참고한다
  (`vendor/ReaderSerial/CSharpSample/`).
- 먼저 `0x3B` 전문으로 최종 응답한 리더기의 결과를 채택하고, 나머지 리더기는 `0x60`으로 무효화한다.
- 채택한 응답의 응답코드가 `00`이면 정상 카드 리딩으로 처리한다.
- `0x3B` 응답 데이터를 파싱해 VAN 요청 데이터를 생성하고, `FNAISCRDVAN`을 호출해 VAN 서버에 결제를
  요청한다.

> **이하 §4.4~§4.6의 후속 처리는 모두 "채택된 리더기" 기준이다.** 응답을 채택한 시점에 나머지 리더기는 이미
> 무효화됐으므로, 재요청·초기화 등은 그 리더기 하나만 대상으로 한다(2026-08-18 확정).

### 4.4 FALLBACK 처리

- IC 리딩 결과 `0x3B` 응답코드가 `07`이면 FALLBACK 거래로 처리한다.
- 알림창을 `BG_IMG_MS` 기반 화면으로 변경한다.
- **응답한 그 리더기에만** `0x2B` 전문을 다시 요청한다(양쪽에 다시 뿌리지 않는다 — 고객이 이미 그 리더기
  앞에 있기 때문). 거래구분은 `F`로 설정한다.

### 4.5 응답코드 12 처리

- `0x3B` 응답코드가 `12`이면 **응답한 그 리더기에만** `0x2B` 전문을 다시 요청한다. 거래구분은 기존과
  동일하게 `ARQo`.

### 4.6 기타 Reader 응답코드 처리

- `0x3B` 응답코드가 `00`/`07`/`12` 이외면 카드 리딩 실패로 처리한다.
- Reader 초기화(`0x60`)를 요청한다.
- POS에 Reader 오류 및 실패 원인을 응답한다.

### 4.7 Reader DLL 연동 실패

- Reader DLL 호출 또는 CALLBACK 처리 자체가 실패한 경우 "DLL 연동 오류"로 처리한다.
- POS에 DLL 연동 오류 및 실패 원인을 응답한다.
- **Reader 응답코드에 의한 실패**(§4.6)와 **DLL 자체 연동 실패**(이 항목)는 구분해서 처리한다.

### 4.8 사용자 취소

- 결제 알림창의 취소 버튼 클릭 시 거래를 취소한다.
- **취소가 가능한 구간은 카드 입력 대기 중(`BG_IMG_IC`/`BG_IMG_MS` 화면)과 PIN 입력 중(§4.12, Phase 18)
  이다.** VAN 서버 통신 중(`BG_IMG_PROCESSING` 화면, §4.10)에는 **취소 버튼을 비활성화**해 누를 수 없게
  한다(2026-08-20 사용자 확정). `FNAISCRDVAN` 요청이 이미 나간 뒤에 취소를 받으면 **VAN 서버에서는 승인이
  났는데 POS에는 취소로 응답하는** 불일치가 생길 수 있기 때문이다. 같은 이유로 ESC 후킹(§5.3)도 이 구간
  에서는 취소로 동작하지 않는다. PIN 입력 중에는 아직 VAN 요청이 나가지 않았으므로 취소·ESC가 그대로
  동작한다(2026-08-27 사용자 확정, §4.12).
- **아직 응답 대기 중인 모든 리더기에** 초기화(`0x60`) 요청을 수행한다(이중화로 2대가 대기 중일 수 있으므로
  한쪽만 정리하면 나머지가 카드를 계속 기다린다).
- POS에 사용자 취소 결과를 응답한다.
- 카드 리딩 CALLBACK과 취소가 동시에 발생할 경우 둘 중 하나의 이벤트만 유효하게 처리되어야 한다(§8).

### 4.9 결제 Timeout

- 카드 입력 대기 시간은 최대 **120초**.
- 120초 동안 카드를 입력하지 않으면 자체 Timeout 처리한다.
- Timeout 발생 시 **응답 대기 중인 모든 리더기에** 초기화(`0x60`)를 수행한다(§4.8과 동일한 이유).
- POS에 Timeout 결과를 응답한다.
- Timeout과 Reader CALLBACK이 동시에 발생하더라도 한 개의 결과만 처리되어야 한다(§8).
- **Timeout은 거래 단위로 하나만 잰다(2026-08-25 사용자 확정)**. "라운드마다 120초를 새로 준다"가
  아니라, 거래를 접수한 순간부터 도는 **하나의 데드라인**이 정본이다 — 그래야 POS 입장에서 "요청을
  보내면 늦어도 이만큼 안에는 답이 온다"가 성립한다(라운드마다 리셋하면 FALLBACK·`12` 재요청이
  겹칠 때 최악 360초까지 늘어난다).
- **단, 사용자가 새로 무언가를 입력해야 하는 단계가 생기면 그때마다 데드라인을 +30초 연장한다**
  (2026-08-25 사용자 확정). 현재 해당하는 것은 FALLBACK(`07`, §4.4)과 재요청(`12`, §4.5)으로 **카드를
  다시 읽어야 하는 경우**다. 이미 120초를 거의 다 쓴 고객에게 "다시 긁어주세요"라고 해놓고 즉시
  Timeout을 내는 것은 부당하기 때문이다.
  - 이 연장 규약은 **앞으로 추가될 사용자 입력 단계에도 그대로 적용한다** — 연장은 "07/12 전용 예외"가
    아니라 **"새 사용자 입력 단계가 시작될 때마다"라는 일반 규칙**으로 구현했다(단계마다 다른 값이
    필요해질 수 있으므로 연장 값은 한 곳에서만 정한다). **PIN 입력(§4.12, Phase 18)이 이 일반 규칙의
    첫 실사용 사례**다 — PIN 전용 예외 분기를 새로 만들지 않고 같은 상수·같은 호출 경로를 그대로
    재사용했다(2026-08-27 확정).

### 4.10 VAN 서버 통신

- 정상 카드 리딩 후(`501008`은 카드리딩 없이 곧바로) VAN 통신 시작 시 `BG_IMG_PROCESSING` 기반 화면으로
  변경한다.
- `FNAISCRDVAN` 호출 시 Mode를 전달한다 — **현재는 `OT`(외부망 테스트) 고정**이며, 운영 환경별 선택
  (`R`/`IT`/`OT`)은 추후 별도 옵션으로 다룬다(2026-08-18 사용자 확정, §11).
- `nRet == 0`이면 DLL 통신 성공으로 판단하고, `outData`의 VAN 응답 전문을 **그대로**(승인/거절 여부를
  원캡이 해석하지 않고) POS에 relay한다(2026-08-26 확정, §3.3) — POS↔원캡과 원캡↔VAN이 같은 전문
  형식이므로 원캡은 순수 중계자다. VAN 응답의 `#7`이 승인(`000`)이든 인터넷지로 응답코드(`111`~`201`,
  `M01`, `V01`)든 카드사 거절 코드든 원캡은 값을 바꾸지 않는다.
- `nRet == -1`이면 VAN DLL 통신 실패로 처리한다(relay할 응답 바이트 자체가 없으므로 원캡이 실패 응답을
  합성한다 — 아래 §4.11 `D` 코드). `out_szRetCode`도 함께 확인해 오류 원인을 판단한다.
- **"VAN DLL 통신 실패"(원캡이 합성하는 실패)와 "VAN 서버 거절"(VAN이 실제로 응답한 거절, 그대로 relay)
  은 서로 다른 경로**다 — 후자는 원캡의 판단이 개입하지 않는다.
- DLL 통신 실패 시 Reader 초기화를 수행하고 POS에 오류 및 원인을 응답한다.

### 4.11 원캡 자체 응답코드 체계 (2026-08-26 확정, Phase 17)

VAN까지 도달한 응답(승인/거절/조회결과 등)은 `#7`에 VAN·인터넷지로가 준 값을 그대로 relay한다(§4.10).
원캡이 VAN에 도달하기 **전** 스스로 실패를 판단하는 경우(취소/Timeout/설정화면 충돌/리더기 실패/전문
오류/VAN DLL 통신 실패)에는 원캡이 직접 `#7`을 채운다 — SPEC이 이미 `M01`/`V01`처럼 주체를 접두 문자로
구분하는 관례를 쓰므로 그 관례를 따르되, SPEC이 실제로 쓰거나 쓸 수 있는 대역(`A`/`B`/`G`/`H`/`M`/`V`/`Z`)
은 피한다.

| 접두 | 주체 | 예 |
|---|---|---|
| `E` | 원캡 자체 판단 | 사용자 취소, 카드입력 Timeout, 설정화면 열림, 리더기 미설정, 무결성 체크 전원 실패, 전문 길이/거래구분 오류, 내부 오류 |
| `R` | 리더기 관련 | 리더기 업무 응답코드 실패(리더기가 준 2자리 코드를 그대로 `R`+코드로), 리더기 DLL 연동 실패(포트 오류/전송 실패/BUSY 등 종류별) |
| `D` | VAN DLL(`KFTC_GIRO.dll`) 연동 실패 | DLL 로드 실패, 호출 자체 실패(`nRet == -1`) |

### 4.12 카드 비밀번호 입력 (PIN, Phase 18 확정, 2026-08-27)

`902614`(신용카드 승인 요청) 전문에만 있는 `#51 암호화된 비밀번호 정보`를 채우기 위해, 카드 리딩 성공
직후 사용자에게 4자리 비밀번호를 입력받는다. `800000`(카드 정보 조회)에는 `#51` 필드 자체가 없어 PIN
단계를 거치지 않는다 — SPEC 어디에도 "PIN이 필요 없는 902614 거래"라는 개념이 없어(§4.12 확정 근거는
`#50 신용카드 승인 인증방식`이 `"2"`(비밀번호 인증) 하나로만 정의돼 있고, "서명/CVM/무서명" 관련 서술이
SPEC 전체에 없는 것) PIN 필요 여부는 **전문 종별로만** 구분한다(902614는 항상, 800000은 절대 아님).

- **화면**: 결제 알림창의 4번째 상태(`PinEntry`, §5.2)로 표시한다. 별도 창을 새로 만들지 않는다 —
  ESC 전역 훅·`Topmost`·취소 게이트·홈 화면 비노출 정책(§5.1/§5.3)을 그대로 재사용할 수 있고, 창 크기
  (750×650)도 바꾸지 않는다.
- **입력 수단**: 화면 키패드(마우스/터치)와 물리 키보드 **둘 다** 지원한다(2026-08-27 실장비 검증 중
  사용자 확정 — 애초에는 터치만 고려했으나 범위 확장). 물리 키보드는 ESC와 같은 이유로 창의 `KeyDown`이
  아니라 **기존 ESC 전역 저수준 훅을 확장**해 처리한다(POS 등 다른 프로그램에 포커스가 있어도 숫자 입력을
  받아야 하므로) — 상단 숫자키/숫자패드 `0`~`9`와 `Backspace`를 매핑하고, PIN 화면이 아닐 때는 소비하지
  않고 그대로 통과시킨다(§4.12 상세는 development_plan.md P18-8).
- **입력 규칙**: 4칸 마스킹 — 누른 숫자를 잠깐 보여준 뒤 마스킹한다. **4자리를 다 누르면 자동 진행**
  (확인 버튼 없음). 한 자리씩 지우는 버튼이 있다. **재입력 기회는 없다** — 비밀번호가 틀려 VAN이
  거절하면 그 응답을 그대로 POS에 relay한다(§4.10 relay 원칙 그대로 적용, 원캡은 PIN 정오를 판단하지
  않는다).
- **취소/ESC**: 그대로 동작한다(§4.8). VAN 요청이 아직 나가지 않았으므로 §4.8의 "VAN 통신 중엔 취소
  불가" 규칙과 충돌하지 않는다.
- **데드라인 연장**: PIN 입력 단계 진입 시 §4.9의 일반 규칙대로 +30초 연장한다(FALLBACK/`12` 재요청과
  같은 경로, 전용 예외 없음).
- **결과 확정 시점**: 카드 리딩 성공 시점이 아니라 **PIN 입력 완료 후 / VAN 진입 직전**으로 결과를
  확정한다 — 그래야 PIN 입력 중에도 취소·ESC·Timeout이 계속 유효하다(이전에는 카드 리딩 성공 직후
  확정해 취소 구독을 끊었는데, PIN 단계가 그 뒤에 오게 되면서 무증상 실패 위험이 생겨 확정 시점을
  옮겼다).
- **`#51` 값**: 입력받은 4자리를 좌측정렬 + space 96으로 채운다(ANS 100). SEED 암호화 방식은 아직
  미정(§10) — 확정 전까지 평문 그대로 채우며, 확정되면 변환 지점 한 곳(`PinFieldEncoder.ToTelegramValue`)
  만 바뀐다.
- **폐기**: 입력된 비밀번호는 카드 리딩 데이터와 동일하게 거래 종료 시 즉시 폐기하고(§8.4), **어떤
  로그에도 값(또는 부분값)을 남기지 않는다** — 자릿수/완료 여부 정도만 기록한다.

## 5. 결제 알림창 요구사항

### 5.1 표시 정책

- 결제 중 사용자에게 보여주는 화면은 결제 알림창만 사용한다.
- 결제 요청 때문에 `KFTCOneCAP.Wpf` 메인 화면(홈 화면)이 전면에 노출되어서는 안 된다.
- 메인 화면이 사용자 조작으로 전면에 올라와 있었더라도 결제 완료 후에는 다시 백그라운드 상태로
  이동해야 한다.
- 결제 알림창은 항상 다른 프로그램보다 상단에 표시한다(`Topmost` 등).

### 5.2 화면 종류

이미지 자산은 `docs/payment_relay/images/`에 확보되어 있다(2026-08-18). 각 화면마다 **기본 크기(750×650)**
와 **`_VERYSMALL` 접미사가 붙은 축소 크기(375×325, 정확히 1/2 배율)** 두 벌이 제공된다 — 추후 알림창
크기 조절 기능(사용자 확정, 아직 상세 요구사항 미정) 대비용으로 보인다. 지금 단계에서는 두 크기 모두
그대로 보관하고, 실제 "크기 조절" 요구사항이 확정되면 그때 배율/전환 트리거를 정의한다.

| 화면 | 기본(750×650) | 축소(375×325) | 용도 |
|---|---|---|---|
| IC 카드 요청 | `BG_IMG_IC.bmp` | `BG_IMG_IC_VERYSMALL.bmp` | §4.3 |
| FALLBACK 카드 요청 | `BG_IMG_MS.bmp` | `BG_IMG_MS_VERYSMALL.bmp` | §4.4 |
| VAN 서버 통신 중 | `BG_IMG_PROCESSING.bmp` | `BG_IMG_PROCESSING_VERYSMALL.bmp` | §4.10 |
| PIN 입력 (Phase 18, 902614 전용) | 자체 제작 레이아웃(카드+자물쇠 아이콘, PIN 4칸, 3×4 키패드) — SPEC 이미지 자산에 대응 화면 없음 | 자체 제작(축소본 없음, 크기 조절 기능 미확정 §10과 동일 사유) | §4.12 |

**이 PRD 범위 밖(요구사항 원문에 없음, 자산만 먼저 확보됨)**: `BG_IMG_LOCK.bmp`/`BG_IMG_QR.bmp`(및 각
`_VERYSMALL` 버전)도 `docs/payment_relay/images/`에 있다 — 이름으로 미루어 잠금 화면/QR 결제용으로
추정되나 이번 PRD의 어떤 흐름과도 아직 연결되지 않았다. 용도가 확정되기 전까지는 사용하지 않는다.

실제 UI 디자인은 이 이미지 파일 기준으로 구현한다.

### 5.3 ESC 키 처리

- 결제 알림창이 표시되어 있는 동안에만 ESC 키를 Hooking한다.
- ESC 키 입력은 알림창의 취소 버튼 클릭과 동일하게 처리한다 — 따라서 **취소 버튼이 비활성화된 구간
  (VAN 통신 중, §4.8)에서는 ESC도 동작하지 않는다.**
- 알림창이 닫히면 ESC 키 Hooking을 해제한다.

## 6. 리더기 설정 화면 요구사항 (기존 화면 기능 연동)

`docs/home_reader_setup/PRD_WPF.md`로 이미 구현된 리더기 설정 화면(1차 범위, UI만)에 다음 실제 동작을
연동한다.

- 초기화
- 상태체크
- 키다운로드 (버튼만 제공, 동작은 §11 추후 구현)
- 무결성체크
- 업데이트 (버튼만 제공, 동작은 §11 추후 구현)

이와 함께 1차 범위에서 "외부 DLL 연동 필요"를 이유로 보류됐던 다음 항목도 이번 범위에서 해소한다.

- **실제 COM 포트 열거** (`docs/home_reader_setup/PRD_WPF.md` §4.13) — `SerialPort.GetPortNames()`, 첫 항목은
  항상 `"미사용"`, 저장된 포트가 목록에 없으면 `"<port>(사용불가)"`로 유지
- **COM 포트 콤보 변경 시 포트 닫고 새 포트로 다시 열기** (§2.2.2 — 이 앱에서 포트를 닫는 유일한 경우)

**이번 범위에서도 계속 제외**(2026-08-18 사용자 확정): AOP 제약 로직(`PRD_WPF.md` §4.11), TRANSINFO_AOP
확인 시 검증(§4.12), 포트 열기 토글(§4.8 — §2.2.2대로 기능 자체를 되살리지 않음).

**설정 화면과 결제 워커의 COM 포트 경합은 양방향 모두 차단한다**(2026-08-25 사용자 확정).

- 설정 화면이 열려 있는 중에 결제 요청이 오면 → 카드 리딩을 시도하지 않고 즉시 오류 전문 반환(§4.7,
  2026-08-25 확정). 설정 화면을 강제로 닫지 않는다.
- 반대로 **거래가 진행 중일 때 사용자가 설정 화면을 열려고 하면 → 열지 않고 안내한다**. 결제 알림창이
  뜨는 순간 홈 화면은 트레이로 내려가므로(§5.1) 실수로 누를 경로는 이미 없지만, 사용자가 트레이
  아이콘으로 홈 화면을 다시 꺼내면 여전히 누를 수 있다 — 그 남은 경로를 이 규칙이 닫는다.
- 두 방향 모두 판정 기준이 "설정 화면이 떠 있는가" / "거래가 처리 중인가" 하나씩뿐이라 애매한 중간
  상태가 없다.

### 6.1 초기화

- Reader `0x60` 요청 → `0x70` 응답. 응답코드 `00`이면 성공.
- 성공: `리더기 초기화 성공`
- 실패: `리더기 초기화 실패\n{실패 원인}`

### 6.2 상태체크

- Reader `0x61` 요청 → `0x71` 응답. 응답코드 `00` 또는 `08`이면 성공.
- 성공 시 `0x71` 전문에서 **리더기 인증 식별 번호**, **모듈 ID**를 파싱해 화면에 출력한다.
- 성공: `리더기 상태체크 성공\n리더기 인증 식별번호 : XXXXX\n모듈 ID : XXXXX`
- 실패: `리더기 상태체크 실패\n{실패 원인}`

### 6.3 키다운로드

- 기능 버튼만 제공한다. 실제 동작은 추후 구현(§11).

### 6.4 무결성체크

1. Reader `0x61` 요청
2. `0x71` 응답 수신
3. 리더기 인증 식별번호/모듈 ID 파싱
4. Reader `0x62` 요청
5. `0x72` 응답 수신
6. `0x72` 응답코드가 `00`이면 성공

- 성공: `리더기 무결성 체크 성공\n리더기 인증 식별번호 : XXXXX\n모듈 ID : XXXXX`
- 실패: `리더기 무결성 체크 실패\n{실패 원인}`

### 6.5 업데이트

- 기능 버튼만 제공한다. 실제 동작은 추후 구현(§11).

### 6.6 리더기 오류 표시 공통사항

- 전문 응답코드에 의한 실패와 Reader DLL 연동 실패를 구분해서 표시한다.
- 가능하면 실패 원인을 사용자에게 함께 출력한다.

## 7. 무결성 체크 정보 저장 요구사항

- 무결성 체크 이력은 SQLite 등 클라이언트용 로컬 DB에 저장한다.
- 저장 항목: 체크 일시, COM Port, 결과, 응답코드, 모듈 ID, 리더기 인증 식별번호, POS 식별번호.

- 리더기 설정 화면의 "무결성 체크 정보" 리스트(`docs/home_reader_setup/PRD_WPF.md` 4.6, 1차 범위에서는
  정적 빈 상태만 구현됨)도 이 DB를 조회해 실제 데이터를 표시하도록 연동한다.

## 8. 거래 처리 및 동기화 요구사항

### 8.1 중복 거래 방지

- 하나의 거래가 완료되기 전 다른 거래가 동시에 실행되어서는 안 된다. 추가 요청은 Queue에서 대기한다.

### 8.2 중복 카드 리딩 방지

- 하나의 거래에서 카드 리딩 결과가 두 번 이상 처리되어서는 안 된다.
- Reader DLL CALLBACK이 중복 호출되더라도 최초 유효 응답만 처리해야 한다.

### 8.3 동시 이벤트 처리

다음이 동시에 발생하더라도 하나의 이벤트만 최종 처리되어야 한다.

- 카드 리딩 완료 + 사용자 취소
- 카드 리딩 완료 + Timeout
- 사용자 취소 + Timeout
- Reader CALLBACK 중복 수신

### 8.4 거래 종료 후 데이터 정리

- 거래 종료 시 그 거래에서 사용한 카드 리딩 데이터를 모두 삭제한다. **"거래"의 단위는 전문 1건이다**
  (2026-08-26 확정, §3.3) — `800000`과 `902614`는 서로 다른 거래이므로 `800000`에서 읽은 카드 데이터를
  `902614`로 넘기지 않고, 각 전문이 끝날 때마다 그 전문이 읽은 카드 데이터를 폐기한다.
- 이전 거래의 Reader CALLBACK/카드 데이터가 다음 거래에 영향을 주어서는 안 된다.
- **PIN(§4.12, Phase 18)도 카드 리딩 데이터와 동일하게 취급한다** — 거래 종료 시 즉시 폐기하고, 다음
  거래에 잔존하지 않는다. **`string`은 메모리에서 0으로 덮어쓸 수 없다**(불변 + 인터닝)는 .NET의 근본
  제약이 있어, "참조를 즉시 끊는 것"까지가 이 애플리케이션 레벨에서 할 수 있는 폐기 수준이다(진짜
  메모리 스크러빙이 필요하면 별도 보안 문자열 타입이 필요한데, 이 범위에서는 다루지 않는다). **PIN
  값은 어떤 로그(일반 로그·예외 메시지 포함)에도 남기지 않는다** — 자릿수/완료 여부 정도만 기록한다
  (2026-08-27 확정).

## 9. 안정성 및 성능 요구사항

- `KFTC_GIRO.dll`이 32bit(x86)이므로 빌드 환경(`PlatformTarget`)을 이 DLL이 로드 가능한 아키텍처로
  맞춰야 한다(`ReaderSerial.dll`과 동일 제약, §2.2/§2.3).
- `KFTC_GIRO.dll` 호출 시 ANSI 문자열 변환과 입출력 Buffer 크기를 정확히 관리해 메모리 침범이 발생하지
  않도록 한다.
- 대상 PC에서 `KFTC_GIRO.dll`의 의존 DLL/런타임이 정상 로드되지 않는 경우에도 프로그램이 비정상 종료되지
  않고 오류로 처리되어야 한다.
- Reader DLL 오류, VAN 통신 오류, Socket 통신 오류로 프로그램 전체가 종료되어서는 안 된다.
- 결제 처리 중 발생 가능한 예외를 충분히 처리해야 한다.
- 장시간 실행 시 메모리 누수가 발생하지 않도록 관리한다.
- 거래 종료 시 CALLBACK, Timer, Hook 등 거래 관련 리소스를 정상적으로 정리한다.
- 카드 리딩 데이터는 거래 종료 후 즉시 삭제한다.
- 결제 처리 속도는 최대한 빠르게 유지하되, **처리 속도보다 중복 거래/중복 카드 리딩 방지가 우선**한다.

  (`Services/Payment/PinFieldEncoder.cs`의 `ToTelegramValue`)만 바뀐다. 발주처 확인 시 SPEC의 표-설명
  불일치도 함께 정정 요청한다.
- ~~POS 응답 결과코드 체계~~ — **해소(2026-08-26)**. `E`(원캡 자체 판단)/`R`(리더기)/`D`(VAN DLL) 3자리
  접두 체계로 확정, 리더기 DLL 연동 실패의 세부 원인(포트 오류/전송 실패/BUSY 등)까지 구분한다. 상세는

**인코딩(CP949)과 패딩 규칙(N=우측정렬 0패딩, 그 외=좌측정렬 space패딩)은 여전히 발주처 확인 대기**
(§3.3, §4.11 구현 근거) — SPEC 원문에 명시가 없어 국내 표준 관례로 진행 중이며, 발주처가 다르게 확정하면
`Protocol/Pos/PosMessageEncoding`/`PosFieldType` 상수 각 1곳만 바꾸면 된다.

**`#46` 암호화된 카드정보(196바이트 고정) 초과 처리는 확정 불필요로 정리**(2026-08-27 사용자 확인) —
실제 운용에서 리더기 응답의 암호화 데이터가 196바이트를 넘지 않는다. 초과 시 예외를 던지는 현재 방어
로직은 그대로 안전장치로 남겨 둔다.

**`#46` 필드 구성 — 2026-09-01 사용자 확정(SPEC 문서 근거 아님)**. SPEC은 이 필드를 "암호화된
카드정보"(AN196)로만 정의할 뿐, 필드 내부에 길이 헤더를 요구한다는 서술이 없다 — 아래 구성은 사용자가
실제 리더기 캡처 데이터를 직접 분석해 확정한 것이며, 이 문서 밖 어디에도(SPEC 원문 포함) 명시적으로
쓰여 있지 않다는 점을 분명히 남긴다.

- 구성: **"0" + 리더기가 응답(0x3B)으로 준 "암호화데이터 길이" 필드값(3자리, zero-padded)** + 그 길이만큼의
  암호화 페이로드. 리더기 응답의 마커(`ENC`/`PON`)와 WCC는 `#46`에 포함하지 않는다 — 길이 헤더(4자리, 첫
  자리는 항상 "0" 고정)와 페이로드만 이어붙인다.
- 총 길이가 196을 넘지 않는 이유: 리더기 SPEC이 정의하는 암호화 데이터 최대 길이가 192바이트이므로
  4(길이 헤더)+192(최대 페이로드)=196 — `#46` 필드 길이(196)와 정확히 일치한다. 페이로드가 192바이트보다
  짧으면 나머지는 기존 `PosField.Pad()`가 하던 대로(AN 타입, 좌측정렬+우측 space 패딩) 자동으로 채워진다
  — 이 구성을 위해 새 패딩 로직을 만들지 않았다.
- 구현: `Protocol/Reader/CardReadResponseParser.cs`의 `CardReadData.EncryptedDataLengthText`(파싱 시점에
  실제로 읽은 payload 길이로부터 `Length.ToString("D3")`로 재구성 — 원래 리더기가 보낸 3자리 길이 필드
  원문과 항상 같다)와 `Services/Payment/PaymentOrchestrator.FillCardApprovalFields`(`"0" +
  EncryptedDataLengthText + EncryptedData`를 `#46`에 write)를 참고.
- 근거: 사용자가 실제 캡처한 리더기 응답 데이터로 직접 확인함(캡처 원문은 암호화 데이터라 민감하므로
  이 문서에는 형식/자릿수 설명만 남기고 실제 바이트를 옮기지 않는다).
- 검증: `--payment-flow-test` 진단 하네스(`Services/Diagnostics/PaymentFlowTestScenarios.cs`)가 `#46`의
  원문 바이트(POSITION 407, 길이 196)를 직접 읽어 헤더("0"+3자리 길이)로 시작하는지, 나머지가 공백으로
  정확히 패딩되는지를 바이트 단위로 확인한다(2026-09-01).
> **멀티패드 설정(`MULTIPAD1_FIELD`/`MULTIPAD2_FIELD`)은 이번 범위에서 사용하지 않는다**(2026-08-19 확정).
> 1차 PRD의 안내 문구(`PRD_WPF.md` §4.10)는 "ON: QR 기능 사용 가능"이라 QR/스캐너 기능을 가리키는데,
> `ReaderSerial.dll`이 말하는 "멀티패드"는 리더기와 핀패드가 한 COM 포트를 공유하는 하드웨어 구성을 뜻한다
> (`docs/reader_dll/DLL연동가이드.md` §6.1) — **같은 단어가 서로 다른 개념을 가리킨다.** 현재 PRD에 핀패드·QR
> 요구사항이 없으므로 이 값을 읽어 쓰지 않으며, `Reader_OpenPort`의 `pinpadCallback`에는 `nullptr`을 넘긴다
