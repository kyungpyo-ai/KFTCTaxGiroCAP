[한글(HWP) 붙여넣기용] "마. 직전 전문 확인 요청" 신규 절 제안
작성: KFTCTAXGIROCAP 개발팀, 2026-09-15

사용법: 본문 목차의 "2. TCP/IP 고정길이 전문" 아래, "라. 국고 신용카드 승인 요청(902614)" 절이
끝나는 지점(문서 p.17 끝, "3. 응답코드" 시작 전)에 아래 내용을 그대로 붙여넣으시면 됩니다. 표 블록은
탭으로 열이 구분돼 있어 붙여넣기 시 "탭을 기준으로 표 만들기"를 선택하시면 표로 바로 변환됩니다(자동
변환이 안 되면 표를 먼저 만든 뒤 셀 단위로 붙여넣어 주세요). 목차(문서 p.3)의 "라." 항목 다음 줄에도
"마. 직전 전문 확인 요청 ······ (쪽번호)" 한 줄을 추가해 주셔야 합니다.

이 절은 본 SPEC 원문(2026-08-31판)에 없던 신규 제안입니다 — POS↔원캡 소켓 연결이 응답 전에 끊겼을
때, POS가 재연결 후 직전 거래(501008/800000/902614 공통)의 처리 결과를 다시 물어볼 수 있게 하는
전문입니다. "나/다/라" 절과 동일하게 공통부(#1~#13)도 이 절 자체 표 안에 다시 담았습니다(SET 장소가
전문마다 달라 각 절이 표를 반복해서 그리는 기존 방식을 그대로 따름). #4 거래구분 코드 "999999"는
임시 채번이며, 발주처 확정값으로 교체 부탁드립니다.

────────────────────────────────────────────────────────────
마. 직전 전문 확인 요청 (POS-원캡 구간 전용, 999999)
────────────────────────────────────────────────────────────

1) 전문 FORMAT

POS ────────────────▶ 원캡        (직전 전문 확인 요청)
POS ◀──────────────── 원캡        (직전 전문 확인 응답 — 원거래 응답 원문 포함)

※ 이 전문은 POS-원캡 구간에서만 사용하며 KFTCVAN·인터넷지로시스템으로 전달되지 않습니다. 원캡이
직전 처리 거래 1건의 결과를 자체 보관했다가 그대로 돌려주는 방식입니다(그래서 아래 표는 항상 공란인
"인터넷지로" 열을 빼고 kiosk/원캡 두 열만 둡니다).

※ #4 거래구분 코드 "999999"는 발주처 협의 전 임시 채번입니다 — 확정되면 이 값만 교체합니다.

※ 요청 전문은 공통부(#1~#13, 70바이트)만으로 끝나며 개별부가 없습니다. #14~#16은 응답 전문에만
있습니다.

※ SPEC 원문 관례상 공통부 다음 개별부는 "구분" 열에 병합 라벨을 붙입니다(501008 "조회정보부",
800000 "정보부", 902614 "납부정보부"). 이 표도 그 관례를 따라 #14~#16을 "정보부"로 묶었습니다.

※ 원본 SPEC 표는 "가. 공통부분"부터 #0(전문 길이)을 첫 행에 포함합니다(번호=0, DATA 항목=전문
길이, 표현=N4, POSITION 공란). 아래 표도 이를 따라 #0부터 시작합니다 — 이 절은 인터넷지로로
나가지 않으므로 #0의 SET 장소는 kiosk(요청 시)/원캡(응답 시) 양쪽으로 표시했습니다.

※ kiosk 열에서 "공백으로 보내는 필드"는 체크를 뺐습니다. ○는 "그 쪽이 실제 값을 채운다"는
뜻이어야 합니다 — 원캡(HandleStatusInquiry)이 이 요청에서 실제로 검사하는 값은 #4(라우팅 판별)와
#9(원거래 매칭 키) 둘뿐이고, 실제 코드(MainForm.cs OnStatusInquiryClickAsync)도 순수 업무값
필드는 손대지 않아 공백으로 나갑니다. 그래서 실제로 값이 채워지는 #4/#9만 "●"(필수)로 표시하고,
공백으로 나가는 순수 업무값 필드(#1,#2,#5,#6,#8,#10,#11,#12,#13)는 체크를 비웠습니다.

※ #3(전문 종별 코드)은 예외로 kiosk ○를 되살렸습니다. 원캡이 요청 값을 검증하진 않지만, #3은
"요청/응답 구분"을 나타내는 프로토콜 골격 필드라 다른 3전문과 동일하게 kiosk가 요청 시에도
"0200"을 채웁니다(요청엔 없고 응답에만 있으면 비대칭이라는 지적 — 코드도 buffer.Write(3, "0200")을
되살렸습니다). #0(전문 길이)도 공백이 아니라 프레이머(TelegramCodec.Encode)가 계산해 넣는 실제
값이라 ○를 유지합니다.

2) 전문 구성 요소 설명

□ (#3)전문 종별 코드
  o 요청 "0200" / 응답 "0210". 다른 전문과 동일한 규칙입니다.

□ (#4)거래구분 코드
  o 직전 전문 확인 전용 신규 코드("999999", 임시). 기존 501008/800000/902614와 중복되지 않는
    값이어야 합니다.

□ (#7)응답 코드
  o "이 조회 요청 자체가 성공했는가"만 나타냅니다 — 직전 거래를 찾았으면 "000"(고정), 못 찾았으면
    "E07"(원거래 없음 — 부록 참고). 원거래 응답의 (#7)을 그대로 relay하지 않습니다(2026-09-15
    재수정) — 원거래가 실제로 승인/거절이었는지는 이 값과 무관하며 (#16)을 파싱해서만 판단합니다.

□ (#9)요청기관 전문 관리 번호
  o 응답을 받지 못한 원거래(조회 대상)에 kiosk가 사용했던 값을 그대로 재사용합니다(이 전문에서만의
    예외 — 다른 모든 전문은 매 요청마다 새로 채번). 원캡은 응답에서 이 값을 그대로 echo만 합니다.
  o 원캡은 저장해 둔 직전 거래 1건의 이 값과 일치할 때만 그 결과를 반환합니다. 원캡은 직전 1건만
    보관하므로 이력 검색이 아니라 단순 일치 비교입니다.

□ (#14)원거래 거래구분 코드
  o 조회 결과가 있으면 원거래의 거래구분 코드(501008/800000/902614)를 그대로 채웁니다. 결과가
    없으면 "000000".

□ (#15)원거래 응답 전문 길이
  o 뒤따르는 (#16)의 바이트 수. 결과가 없으면 "0000".

□ (#16)원거래 응답 전문 원문
  o 원캡이 보관해 둔 원거래 응답 전문을 파싱·재해석 없이 원문 그대로 싣습니다. 결과가 없으면 필드
    자체가 생략됩니다(0바이트, 응답 전문은 80바이트로 끝남).
  o kiosk는 이 값을 잘라내 원거래 종류(501008/800000/902614)에 맞는 기존 응답 파서를 그대로
    재사용해 처리합니다 — 이 전문 자신을 위한 별도 파서를 새로 두지 않습니다.
